# DeepFlow（deer-flow）多轮对话 agent 接入说明

- 日期：2026-09-15
- 范围：**只影响新链路**（`agent.html` 对话式画布）；老配置页与单轮取数保持原样
- 结论：多轮对话的**意图判定**已从纯关键词规则切换为 deer-flow 的 LangGraph agent（`fz-canvas`），
  规则路由降级为**槽位解析**（品牌 / 页码 / 时间窗）。取数、画布卡、SQL 全部仍走原链路与真实 MySQL。

---

## 1. 为什么这么做 / 之前是什么样

| | 改造前 | 改造后 |
|---|---|---|
| 意图判定 | `intent_router.py` 纯关键词加权打分（88 词表），零命中 → `unknown` 追问 | deer-flow agent `fz-canvas` 读上下文，输出结构化 JSON |
| 多轮上下文 | 只有工作记忆（品牌、已选维度） | LangGraph thread 级对话历史（checkpointer 持久化）+ 工作记忆 |
| 说「你好」 | 关键词零命中 → 追问（不出卡） | LLM 判定为 `chat`，自然语言回应 + 澄清问题（仍不出卡） |
| 说「把这两个图串成汇报」 | 依赖「汇报/PPT」等词命中 | LLM 结合 thread 上下文判断指向哪两张图 |

**没有变的**：所有数据仍来自真实 MySQL；画布卡仍由 `conversation_service` 写；老接口与老页面未改。

## 2. 组件与拓扑

```
浏览器 agent.html
   │  POST /api/v1/conversations/{id}/messages
   ▼
fz 后端 127.0.0.1:18900   ConversationService.handle_message
   │  ① 规则路由 → 只取槽位（brand / page_count / time_window）
   │  ② deepflow_agent_service.plan_turn(...)  ───────┐
   │  ③ 按 LLM 判定分发到 _handle_explore / _handle_data_query / ... │
   ▼                                                  │
真实 MySQL dataservice_test_local                     │ HTTP（不走代理）
                                                      ▼
                          DeepFlow agent 127.0.0.1:2124（langgraph dev）
                                                      │
                                        agent `fz-canvas`（deer-flow lead_agent 图）
                                                      │
                                        模型 fz-gpt-5.2 → 内网网关 20.255.59.22:4000
```

- **thread 映射**：`thread_id = uuid5(固定命名空间, "fz-" + conversation_id)`。
  LangGraph **只接受 UUID** 形式的 thread id，所以用确定性 uuid5 派生：同一会话永远同一个 thread，
  不需要额外存映射表，重启后靠 checkpointer（sqlite）继续。
- **checkpointer**：`deer-flow/backend/.deer-flow/checkpoints.db`（deer-flow 自带配置）。
- **gateway / frontend / nginx 都不需要起**：画布链路只用到 LangGraph 的
  `POST /threads` 与 `POST /threads/{id}/runs/wait`。

## 3. agent 契约

### 3.1 输入（作为 human 消息的 JSON）

> **2026-09-20 改版**：不再传 `has_charts` / `has_outline` / `can_rollback` / `chart_dimension_keys`
> 这类**按产物类型的布尔开关**，改为传一份**自描述的画布快照**。原因见第 8 节。

```json
{
  "user_text": "用户这一轮的原话",
  "scene": {"scene_id": "scene_prd_competitor", "name": "竞品与价格分析"},
  "brand_memory": "ZARA",
  "canvas": {
    "artifacts": [
      {
        "kind": "outline_card",
        "title": "ZARA汇报大纲",
        "subtitle": "4 页 · 已绑定 1 页图表",
        "status": "ready",
        "detail": {"pages": "4 项", "status": "ready", "dedupe_key": "main"}
      }
    ],
    "rollback_available": true
  },
  "last_turn": {"intent": "canvas_revision", "system_result": "已更新画布：outline_card《ZARA汇报大纲》"},
  "dimension_options": [
    {"dimension_key": "price", "title": "价格带与折扣节奏", "angle": "…", "dimensions": ["二级类目"], "metrics": ["价格"]}
  ]
}
```

要点：

- `canvas.artifacts[]` 由 `conversation_service._artifact_digest` **通用投影**得出：
  不写任何 `kind` 分支，只按值类型折叠（超长串丢弃、列表/字典 → `"N 项"`、bool/None 丢弃）。
  新增产物类型**不需要改这段代码**，agent 也能看见它。
- `canvas.rollback_available` = 画布上是否有任意产物存在历史版本（可直接回退）。
- `last_turn.system_result` 是**上一轮系统实际做了什么**（「已更新画布：…」/「本轮未执行（error）」/
  「画布未变化」），让 agent 能区分"我以为改了"和"真改了"。
- agent 看到的是**事实**（画布上有什么），不是**能力开关**（有没有大纲）。这是本轮改造的核心：
  「有没有大纲」这种问题应该由它自己从 `artifacts` 里读出来，而不是靠后端喂一个布尔值。

### 3.2 输出（严格 JSON）

```json
{
  "intent": "chat | explore | data_query | report_build | canvas_revision | rollback",
  "dimension_keys": ["price"],
  "time_window": "近3个月",
  "page_count": null,
  "reply": "给用户看的中文回复",
  "needs_clarification": false,
  "clarify_question": ""
}
```

### 3.3 后端侧校验（防幻觉的三道闸）

1. `intent` 不在白名单 → 归一为 `unknown`（走追问）。
2. `dimension_keys` **必须**存在于真实维度选项里，否则丢弃；若 `data_query` 最终没有有效 key → 追问，不出卡。
3. 解析不出 JSON → **不猜**，返回 `unknown` + 追问（`parse_failed=true` 便于排查）。

`page_count` 被夹到 2~12。

## 7. 已知边界与注意事项

1. **每轮多一次 LLM 调用**（约 5~20s），首字延迟比纯规则高；这是"真多轮"的代价。
2. **代理坑（最坑的一个，已修）**：运行环境（含沙箱）注入了 `HTTP_PROXY/HTTPS_PROXY`，
   deer-flow 里的 httpx/openai 客户端默认 `trust_env=True` 会把它们用上，于是请求行被写成
   **绝对 URL 形式**：`POST http://20.255.59.22:4000/v1/chat/completions`
   而不是 `POST /v1/chat/completions`。内网网关对这种畸形请求行**直接回 404**。
   症状极具迷惑性：**同一会话第 1 轮正常、第 2 轮起必失败**（`openai.NotFoundError: 404 {'detail': 'Not Found'}`），
   而用 `curl` 直连网关连打几十次全 200。
   **修复**：`scripts/start_deerflow_agent.sh` 启动时显式
   `env -u HTTP_PROXY -u HTTPS_PROXY -u ALL_PROXY -u http_proxy -u https_proxy -u all_proxy … NO_PROXY='*'`
   （该 agent 只访问内网网关与本机，永远不需要代理）。
   定位手段：在 `127.0.0.1:4001` 起一个记录 `method + path` 的转发代理，把 `config.yaml` 的
   `base_url` 临时指过去，日志里能直接看到绝对 URL —— **不要靠猜，看请求行**。
   同理，桥接层（fz 后端 → 127.0.0.1:2124）也用显式「不走代理」的 opener。
3. **不要只看「端口被监听」判断服务活着**：见第 5 节启停脚本的说明（stop→start 竞态曾导致静默失败）。
4. **agent 不可用时的行为**：返回 `intent=unknown`、`status=failed`、明确文案——不退回关键词猜测。
   文案**按失败所在的那一层**分三种说法（`describe_agent_failure`）：
   agent 服务连不上 / agent 服务通但它没给判定 / 其它；判据是**失败现场探测** agent `/ok`，
   而不是猜错误字符串（2026-10-07 修订，详见
   `docs/配置按需加载_轮次级配置_设计与落地_2026-10-06.md` §6.7——早先那句
   "请确认 deer-flow 的 LangGraph 服务已启动" 曾把责任归错层）。
5. **deer-flow 是旧版 checkout（2026-03-23）**，按用户要求**本次不升级**。若日后升级到上游最新版，注意：
   - 上游把 checkpointer 从 `agents/checkpointer/` 迁到 `runtime/checkpointer/`，`langgraph.json` 结构也变了；
   - 上游 gateway 新增 `/api/runs/stream`、`/api/threads`，聊天入口从「nginx → LangGraph 平台 API」
     收编进 gateway 自身——届时本桥接层的 URL 需要相应调整；
   - 上游根目录不再有 `config.yaml`（改为 `config.example.yaml`），升级时需迁移本文件里的模型配置。
6. **SOUL.md 的措辞会影响判定质量**：它需要明确压掉 deer-flow 通用模板里的深度研究/引用/子代理要求，
   否则模型会输出研究报告体而不是 JSON。

## 8. 画布出现时机：判定边界（2026-09-16 补）

> ⚠️ **本节的具体做法已被第 9 节取代**（拿掉 `has_outline` 这类能力开关，改为自描述画布快照）。
> 但这里记录的两个 bug 与"不猜"的原则仍然有效，保留作历史。

用户反馈两例「不该出画布却出了」，逐条查实并修掉：

| 用户原话 | 修前 | 根因 | 修后（实测） |
|---|---|---|---|
| 「你能做什么事？全面性的？」 | `explore` → 插「分析切入点」卡 | SOUL 只把 `chat` 写作「用户只是问你能做什么」，模型没遵守 | `chat`，**0 张卡**，只回一段能力说明 |
| 「我不是要看这些画布」 | `canvas_revision` → **凭空生成一份汇报大纲** | ① agent 的输入里**没有 `has_outline`**，它无从知道画布上有没有大纲；② 后端 `_handle_revision` 在「没有大纲」时**自己造了一个**（兜底） | `chat`，画布不变；即使模型误判为 `canvas_revision`，后端也改为追问、不造大纲 |

改了三处，都是"不猜"原则的落地：

1. **补上下文**：桥接层 payload 增加 `has_outline`（`deepflow_agent_service.plan_turn` +
   `conversation_service._plan_turn_with_agent`），agent 才有依据拒绝 `canvas_revision`。
2. **删兜底**：`conversation_service._handle_revision` 在 `outline is None` 时**不再新建大纲**，
   改为纯文字追问。这是用户 2026-09-14 明令禁止的"猜"的又一处残留。
3. **收紧 SOUL 规则**：新增硬性规则 5/6（"不许在用户没要求时出卡"、"改画布前提是画布上真有东西"），
   明确「不要／不想看画布」这类**否定与拒绝一律判 `chat`**，并补两条判定示例。

单测：`apps/vibe_backend/tests/test_canvas_revision_guard.py`（断言"无大纲时不得造大纲"）、
`test_deepflow_agent_service.py`（断言 payload 里**不再出现**按能力开关的字段）。

**注意**：`_handle_report_build` 仍会创建大纲——那是用户明确要汇报时的**正当**行为，与兜底无关。

## 9. 从「能力开关」改为「自描述画布」（2026-09-20）

### 9.1 用户质疑

> 「新功能的流程设计是不有问题啊。不是让你接入 deepflow 作为智能交互吗？交互过程当中要自动
> 能够根据输入上下文作出正确的回应。而不是硬编码或者必须提示有没有大纲。」

第 8 节的做法虽然修掉了两个具体 bug，但**方向错了**：给 agent 补一个 `has_outline` 布尔值，
本质上是把「怎么理解上下文」这件事继续留在后端硬编码里——每遇到一种新产物、一种新问法，
就要再加一个开关。agent 拿到的是**结论**（"没有大纲"），不是**依据**（"画布上有这三样东西"）。

### 9.2 改动（四处，全部是"把判断权交回去"）

| 位置 | 改前 | 改后 |
|---|---|---|
| `deepflow_agent_service.plan_turn` | 入参 `has_charts / chart_dimension_keys / can_rollback / has_outline` | 入参 `canvas_state / last_turn` |
| `conversation_service._canvas_state` | 无 | 遍历 `working_memory.produced_artifact_ids` → `{artifacts:[...], rollback_available:bool}` |
| `conversation_service._artifact_digest` | 无 | **通用投影**：按值类型折叠，不写任何 `kind` 分支 |
| `conversation_service._last_turn_context` | 无 | 倒查最后一条 assistant 消息 → 「已更新画布：kind《title》」/「本轮未执行」/「画布未变化」 |
| `fz-canvas/SOUL.md` | 规则 6 条，含"依据 `has_outline` 判断" | 规则 8 条，删掉开关字面规则，新增「先理解意图不要字面匹配」「以 `canvas.artifacts` 里真实存在的产物为前提」「不要为了显得有产出而出卡」「canvas 和 last_turn 是你的眼睛」+ 一节「容易判错的情形」 |

## 10. 两个真实缺陷及修复（2026-09-20）

### 10.1 改完大纲回退不了（版本号推不上去）

**现象**：改完第 2 页，回复说"大纲已更新"，但卡 `version` 仍是 1、`history` 为空 →
`rollback_available=false` → 用户说"撤回"时 agent 只能答"目前画布状态显示还不能回退"。

**根因**（两层，都在 `_handle_revision`）：

1. `report_composer.replace_page` / `remove_pages_by_dimension` 是**原地修改并返回同一个列表对象**。
   代码里 `pages = list(outline.payload["pages"])` 拿到的是浅拷贝列表，元素仍是同一批 dict，
   改一个就改了已存档的 payload。
2. 于是 `changed = pages != outline.payload["pages"]` **永远为 False**（自己跟自己比），
   `push_version=changed` 就一次都没触发。

顺带还有第三个坑：`_upsert_artifact` 写历史快照时存的是 `existing.payload` 的**引用**，
下次编辑会把快照一起改掉——版本号涨了却等于没救。

**修复**：`_handle_revision` 里 `before_pages = copy.deepcopy(...)` 后再改；
`changed = pages != before_pages`；`_upsert_artifact` 的历史快照改为 `copy.deepcopy(existing.payload)`。

守测试：`test_revision_pushes_a_version_so_it_can_be_undone`、
`test_repeating_the_same_revision_does_not_inflate_versions`（内容没变就不推版本）。

### 10.2 确认动作不幂等（点一次变成两条回复）

**现象**：`conv_7a4cccfb49` 里同一条助手回复重复出现 **17 次**，澄清卡 `version=18`。

**根因**：`_apply_resolution` / `_apply_clarification` **每次调用都会重新跑一遍 `_execute_goals`
并再追加一条 assistant 消息**。前端 `applyArtifact` 只置了 busy 提示、没有禁用选项按钮，
双击/重试/网络重发都会线性放大。另外澄清卡答完后**没有任何"已结算"标记**，
连"判断它是否答过"都做不到。

**修复**：在 `apply_artifact_action` 入口加最小幂等闸门——
`resolution_card` / `clarification_card` 若已结算（`payload.status == "resolved"` 或 `card.status == "ready"`），
直接返回 `{"ok": true, "idempotent": true, "artifact": …, "canvas": …}`，**不重新执行、不追加消息**；
并让 `_apply_clarification` 执行成功后写入同样的标记。

**刻意不拦 `chart_card`**：参数抽屉本来就允许反复重跑同一个维度。

**实测**（会话 `conv_a64feba6f3`，真实 HTTP，连点 5 次）：

```
提交前：消息 2 条
 第 1 次提交：idempotent=False ok=True     ← 正常执行
 第 2~5 次提交：idempotent=True  ok=True   ← 全部无操作
提交后：消息 3 条（只 +1）
```

守测试：`tests/test_checkpoint_idempotency.py`（8 项，只打桩取数引擎、不伪造业务结果）。

## 11. 图表白屏：`chart_type="column"` 被 ECharts 静默丢弃（2026-09-20）

### 11.1 现象

用户截图：画布是对的（「共 3 个产物」），纤维混纺那张**面积图正常**，但
**「价格带与折扣节奏」整块是空的**——只剩底部一排旋转的 x 轴类目名，没有 y 轴、没有柱子；
下面的「数据洞察」又有内容（「59979元以下 在SKU数上累计占比最高，约 98.8%」）。
数据明明在，图却是白的。

### 11.2 定位（不猜，全部从真浏览器里读出来）

数据先排除：接口返回 spec 里 `rows` **45 行真实数据**、`y_field=SKU数` 是数字、
`series_field=价格带` 有 5 个取值（命中 37/4/2/1/1 = 45）。

再进 Chromium 探 `echarts.getInstanceByDom(holder).getOption()`：

| 卡 | chart_type | xAxis 类目数 | series 条数 |
|---|---|---|---|
| `art_0150f63427` 纤维混纺 | `area` | 3 | **12**（正常） |
| `art_4ad2417b55` 价格带 | `column` | 37 | **0** ← |

离屏对照实验（同一个 ECharts 实例，只换 `series[].type`）：

```
type: "bar"    → getOption().series.length = 1   ✅
type: "column" → getOption().series.length = 0   ← ECharts 不认识，整条 series 被吞掉
```

**根因**：后端 `chart_spec_service` 的默认类型是 `"column"`（它在 `allowed` 集合里，
第 158/162 行明确返回 `"column"`）；老配置页用 SVG 自绘，`bar`/`column` 都认，所以一直没问题。
但新画布用的 **ECharts 只有 `bar`**，而 `agent.js` 的 `buildOption` 只映射了
`area→line`、`bar→bar`，**`"column"` 原样透传** → ECharts 静默丢 series →
只剩坐标轴，不报错、不打日志。下拉框第一个选项恰好就是 `column`，所以这是默认路径。

### 11.3 修复（只改前端，不动后端契约、不动老页面）

`apps/vibe_frontend/static/agent.js` 的 `buildOption`：

```js
var chartType =
  type === "area" ? "line" :
  type === "column" || type === "vertical" ? "bar" :
  type === "bar" ? "bar" : type;
```

顺带把 `stack` 按后端契约落实：`stack: spec.stack ? "total" : undefined`
（后端对 `column`/`area` 明确要求堆叠；旧代码只对 line 生效，导致柱状图不堆叠）。

**为什么不在后端把 `column` 改成 `bar`**：`"column"` 是老配置页的合法取值，
后端契约一改就同时影响老功能——违反"老功能流程不要变"。

### 11.4 验证（真浏览器，逐类型过一遍）

| 下拉框取值 | 映射到 | ECharts 是否保留 series |
|---|---|---|
| `column` | `bar` | ✅ 1（修复前 **0**） |
| `bar` | `bar` | ✅ 1 |
| `line` | `line` | ✅ 1 |
| `area` | `line` | ✅ 1 |

修复后实际那张卡：`seriesLen: 5`，全是 `type: "bar"`、`stack: "total"`，
非空值 37/4/2/1/1，x 轴 37 个类目 —— 与真实 45 行完全吻合（见
`docs/evidence/2026-09-20_价格图修复后.png`）。

**回归闸门**：`scripts/verify_chart_type_mapping.py` —— 断言下拉框里每一种类型
要么本身就是 ECharts 认识的类型，要么在 `buildOption` 里被显式翻译过。
已做正反两面验证：去掉映射立刻非零退出并点名 `column`。

### 11.5 次生坑：改了 JS 用户却还看到旧页面

`?v=` 缓存戳升了、文件也换了，浏览器里却仍是旧脚本。原因是前端用
`python -m http.server`，**它不返回 `Cache-Control`**，浏览器就按启发式规则
（基于 `Last-Modified`）自己决定缓存 `agent.html` 多久——**被缓存的是 HTML 本身**，
它引用的还是老 `?v=`，于是缓存戳升级形同虚设。

**修复**：新增 `scripts/serve_vibe_frontend.py`（只是给 stdlib 的
`SimpleHTTPRequestHandler` 补 `Cache-Control`），`start_vibe_frontend.sh` 改用它：

| 请求 | Cache-Control |
|---|---|
| `agent.html` | `no-cache`（允许缓存，但每次必须回源校验） |
| `agent.js?v=...` | `public, max-age=31536000, immutable` |
| 其他未带版本戳的静态资源 | `public, max-age=300` |
