## 2. 当前状态判断

已具备：

- 数据库 schema 驱动的表、字段和关系推荐。
- 场景描述与推荐目标分离，以及推荐结果人工确认状态保留。
- 语义字段/关系的手工补充、导入导出和配置迁移。
- 品牌、品类、纤维等受控字段的标准值召回、归一化和歧义确认。
- 自适应价格带、分桶边界和策略记录。
- 新旧服装数据结构兼容，以及服装到纤维字典的多表查询。
- 基础查询、结果历史、Slide Draft、Deck 和 TrainPPTAgent handoff/callback 链路。

主要缺口：

- SQL 校验仍需要升级为 AST 级安全规则并形成可回归的拒绝案例集。
- 场景配置已有导入导出，但缺少稳定的草稿、发布、版本差异和回滚工作流。
- 会话与 Deck 虽有持久化代码，仍需验证重启恢复、连续追加和幂等行为。
- 结果、图表、结论和 SQL 的页级 lineage 还需要统一契约并完整落库。
- DeepFlow 仍需从可选旁路能力收敛为稳定的会话记忆与任务编排能力；PPT 页面编辑统一由 TrainPPTAgent 承担。
- 缺少面向真实客户库的自动化回归、运行监控和部署验收基线。

## 4. 建议迭代顺序

### 迭代 0：可信查询基线（约 1 周）

1. 冻结一份客户库 schema 和最小场景配置。
2. 建立 10-20 条 golden questions，覆盖品牌区域、品类歧义、纤维多跳和价格带。
3. 完成 AST 只读/白名单/关系/结果上限校验。
4. 将校验失败、标准值未命中和歧义未确认纳入统一错误结构。

这一迭代完成后，系统才适合继续扩展场景，否则每个新模块都会放大查询口径问题。

### 迭代 1：可治理配置与可恢复会话（约 1-2 周）

1. 建立场景配置版本、发布、差异和回滚。
2. 完成 schema snapshot 与刷新影响提示。
3. 补齐 session/query/slide/deck 的恢复和幂等测试。
4. 固化 QueryResult、ChartSpec 和 lineage 字段。

这一迭代完成后，业务人员可以安全维护场景，开发人员可以定位一次结果从问题到页面的完整链路。

### 迭代 2：报告生产化（约 1-2 周）

1. 固化 TrainPPTAgent handoff/callback 协议和编辑器地址配置。
2. 支持 Slide 编辑、审核、批准入 Deck 和持续追加。
3. 增加公司模板、主题色、封面/总结/来源页配置。
4. 做 handoff、编辑回写、页序和版本冲突验收。

## 5. 暂不进入本阶段

以下事项继续保持在核心闭环之后：

- 复杂登录、权限、多租户和多人协作。
- 自动爬虫、ETL 和业务库写回。
- 同款识别、复杂指标平台和全量 RAG 知识库。
- 高度定制的企业模板中心和定时报表推送。

## 6. 下一步直接开工项

建议下一次开发直接从 P0 开始：

1. 新增 `docs/test_cases/`，沉淀首批 golden questions 和预期口径。
2. 在 `schema_validation_service.py` 增加 schema snapshot、字段/关系校验入口。
3. 引入 `sqlglot`，在 `query_service.py` 和 `sql_result_agent_service.py` 前增加统一 AST 校验层。
4. 为品牌区域歧义、跨表纤维查询、价格带参数和未确认候选补齐接口回归测试。
5. P0 通过后，再开始配置版本和会话恢复，不与 PPT 接入同时扩散范围。
