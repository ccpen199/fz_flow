## 写下一期时的四条规矩

1. **先读上一期文末的「遗留清单」**。每期都留了一份带日期的开放事项，下一期逐条交代
   「已关 / 仍开 / 新开」，**不要另起炉灶重述** —— 这是"借鉴"的唯一落点。
2. **覆盖区间写死在开头**（`2026-MM-01 ~ MM-末日`）。文件名不带月份，靠本表区分。
3. **体例**：10 条左右，每条一段话，写「做了什么 + 解决了什么问题」，技术细节放括号里；
   末尾附「本期主要产出」与「遗留清单」两张表。
4. **依据是工作区文件 + 当期文档 + 代码改动，不是 git 提交历史** ——
   本项目很长一段时间改动没有提交（`git status` 里是一大批未跟踪文件），按提交归期会漏掉全部内容。

## 素材在哪（从仓库根看）

| 素材 | 位置 | 说明 |
| --- | --- | --- |
| 逐日流水 | `.workbuddy/memory/YYYY-MM-DD.md` | 最详细，含踩坑、实测数字、**追加式**（只增不改） |
| 长期结论 / 硬约束 | `.workbuddy/memory/MEMORY.md` | 跨期有效的约定与已修缺陷 |
| 当期成文文档 | `docs/*.md`、`docs/*.html` | 按文件名里的日期归期 |
| 验收截图 | `docs/验证_*.png`、`docs/evidence/` | 按文件名里的日期归期 |
| 守卫与自查 | `scripts/verify_*.py`、`scripts/verify_canvas_all.sh` | 判断"当时是否真的跑通" |

⚠️ **归期的坑**：`docs/` 里有些文档的**内容日期与修改日期不一致**（例如
`PPT模块资料总结与方案对比.md` 内容是 2026-05-09、文件是 9 月改的）。
归期一律以**文件修改时间**为准，内容日期只作参考。
