# 第三期工作总结：配置中心推荐、语义消歧与价格带优化

记录范围：截至 2026-09-04。以下为上一期工作总结的落盘版本。

1、完善了服装商品数据智能分析工作台的配置中心推荐流程。
在人工筛选字段和关系之前，补充了从数据库结构中读取表、字段、字段类型、字段注释、主键、外键和关系候选的能力，让系统可以先根据数据库结构和业务描述推荐字段、表关系，再由人工确认进入场景配置。

2、优化了“场景描述”和“推荐目标”的使用逻辑。
场景描述作为长期业务方向，用来告诉系统这个场景主要解决什么问题；推荐目标作为本次推荐的临时重点，用来让同一个场景下可以按不同分析目的返回不同字段和关系候选，比如品牌价格分析、材质分析、品类结构分析。

3、优化了 LLM 推荐字段和关系后的人工筛选流程。
修复了切换推荐目标后已选择字段/关系丢失的问题，保证推荐列表变化时，已经人工确认过的字段和关系不会被清空，避免重复筛选。

4、完善了语义配置区的自定义能力。
支持在底部语义配置区手工新增字段和关系，用来补充 LLM 没有推荐出来、但业务确认需要的表字段和关联关系。比如 `clothing_info.Id = clothing_fiber_info.ClothingId`，以及 `clothing_fiber_info.Code = fabric_fiber_info.Code` 这类两段式关系，可以人工配置后进入后续查询链路。

5、针对品牌和品类匹配不准确的问题，梳理并优化了标准值识别和歧义消解流程。
解决客户提出的大小写、空格、字符差异、品牌区域备注等问题的处理方向：用户输入品牌或品类词后，系统先去标准值库和受控字段中召回候选，如果一个词命中多个字段或多个标准值，先让用户确认，再生成 SQL，避免模型直接用 `LIKE '%uniqlo%'` 造成 `UNIQLO（中国）` 和 `UNIQLO（日本）` 混算。

6、优化了价格带分桶逻辑。
原先价格带是固定模板，客户反馈不同品牌价格区间不一定适合同一套固定分桶。现在改成默认自定义/自适应分桶，支持设置桶数、分桶策略和边界处理。用户只有在问题涉及“价格带、价格区间、分桶”时，页面才展示价格带参数，避免无关问题干扰查询。

7、补充了价格带参数的页面交互说明。
页面支持选择分位数、等宽、边界处理、中间边界等参数，并在结果历史里保存本次使用的价格带策略，方便回看某次结果到底是按几桶、什么策略、什么边界算出来的。

8、验证了服装与纤维成分的多表关系查询路径。
针对“通过服装查纤维成分占比”的需求，确认关系链路是：`clothing_info.Id` 关联 `clothing_fiber_info.ClothingId`，再用 `clothing_fiber_info.Code` 关联 `fabric_fiber_info.Code`，最终拿到标准纤维名称和占比。这说明底部语义关系配置可以支撑这类多跳查询，但前提是字段和关系要配置进场景。

9、对比了 `banana-slides` 项目的数据库结构抽取能力。
明确了 `fz_workflow` 应该吸收它在数据库 schema 抽取、业务描述参与推荐、关系候选生成上的优点，把这些能力放到配置中心前置流程里，而不是完全依赖人工从空白状态挑字段。

10、继续处理了本地和远程运行环境问题。
包括启动脚本、前后端端口、远程仓库同步、Windows 环境适配、不同机器数据不一致导致的结果差异排查，保证项目在不同机器上能尽量按同一套流程运行和验证。
