# 会话式分析智能体 + 动态画布：改造评估与实施规划

版本：v1（评估稿，不含代码改动）
日期：2026-09-14
范围：仅评估「要做什么改动、要加什么新功能」，不含开发

---

## 0. 一句话结论

现有系统已经完成「场景配置中心 → 语义字段消歧 → SQL 生成与执行 → 结果展示 → 报告工作流（大纲/SQL/图表/洞察/审批）→ PPTX 导出 + TrainPPTAgent 交接」的后端主链。

新需求的本质**不是新增一个功能模块，而是交互范式切换**：

| 维度 | 现状 | 目标 |
|---|---|---|
| 入口 | 先选场景 → 切「查询执行」Tab → 填意图 | 直接说一句话（"分析下 Zara"） |
| 交互 | 表单 + 按钮 + 分步确认 | 对话流驱动，边说边出结果 |
| 右侧 | 表单结果区（表格/JSON/预览） | 自演进画布（标签卡 → 图表卡 → 大纲 → PPT 预览） |
| 节奏 | HITL 强制逐节点确认 | 自动推进为主，编辑/回退为辅 |
| 产出 | 单点结果 + 报告脚本 | 对话即报告，终态是可直接汇报的 PPT |

**复用判断**：后端约 60–70%（取数、SQL、洞察、报告计划、PPTX 导出、版本回退）可复用；需要新建的集中在**会话编排层（意图路由 + 维度推荐 + 画布产物协议）**和**前端（对话流 + 图表渲染 + 画布编排）**。

这是一次**重构前端 + 加一层编排**的工程，不是推倒重来。

## 2. 需求拆解：四个阶段 × 三层职责

按你提供的第二阶段表格，逐阶段映射到现有能力：

### 阶段 1：意图启发（模糊探索与维度推荐）

- **用户**：抛模糊想法（"分析下 Zara"）
- **左对话层（新建）**：锁定品牌 → 结合数据资产 + 企划节点，**发散推荐 3 个维度**
- **右画布（新建）**：浮现 3 张可交互**维度标签卡**
- **底层引擎（复用+新建）**：场景字段/样例目标（复用）+ 维度推荐器（新建）

### 阶段 2：即时看数（下钻分析）

- **用户**：点选两个标签，"先看纤维混纺和价格带"
- **左对话层**：解析实体+统计逻辑，派发取数指令
- **右画布**：**原地渲染**图表卡（堆叠面积图 / 柱状图），带数据明细 + **SQL 展开**
- **底层引擎**：自然语言 → SQL → 执行 → 绑定图表 Spec（**全部复用** `sql_result_agent_service` + 新建 ChartSpec 标准化 + 前端渲染）

### 阶段 3：脉络梳理（报告大纲化）

- **用户**："这两部分适合做汇报，帮我串个 4 页 PPT 思路"
- **左对话层**：梳理叙事逻辑，把散落数据整合为多页大纲
- **右画布**：图表**上方升起大纲编辑器**，已出图自动挂载到对应页
- **底层引擎**：监听大纲中是否有**未取数的页面**（新建）

### 阶段 4：交付生产（微调确认与终态）

- **用户**："色彩先不要了，第 4 页换成落地建议，没问题直接生成 PPT"
- **左对话层**：调度全局文案，驱动幻灯片渲染
- **右画布**：平滑切换为 **PPT 预览/编辑模式**（16:9、原地改字、翻页、导出）
- **底层引擎**：对大纲缺数据的页面补执行 SQL 并绑图（复用 + 新建编排）

> 关键差异：现状这条链是「按钮推进 + 每步人工确认」；目标这条链是「**对话触发 + 自动推进 + 随时可介入**」。链路本身（取数→图表→文案→PPT）已经存在，缺的是**驱动方式和表现层**。

┌──────────────────────────────────▼─────────────────────────────────────────┐

│   ConversationService · IntentRouter · DimensionRecommender                  │

└──────────────────────────────────┬─────────────────────────────────────────┘

│ ② 领域服务层（大部分复用）                                                  │

### 4.1 新增组件职责

| 组件 | 职责 | 输入 → 输出 |
|---|---|---|
| `ConversationService` | 会话消息的读写、轮次与产物绑定 | 用户消息 → MessageDTO + artifact_refs |
| `IntentRouter` | 语义识别，决定走哪条分支 | 消息 + 工作记忆 → `{intent, target, entities}` |
| `DimensionRecommender` | 发散推荐分析切入点 | 品牌/场景 + 数据资产 → 3~5 张维度卡 |
| `CanvasOrchestrator` | 把领域服务结果编排为**画布指令** | 意图结果 → 画布 action 列表（插入/更新/切换卡片） |
| `ArtifactService` | 统一产物（卡片）存取与 lineage | artifact_id → 产物 + 来源（message/query/sql） |
| `WorkingMemory` | 多轮上下文（已选维度、已出图、当前稿件） | turn → 状态摘要 |
| `ChartSpecService` | 图表契约标准化（前端渲染与 PPTX 共用） | rows + binding → ChartSpec |
| `ReportComposer` | 对话 → 大纲 → 页面内容 → 绑定已有图 | 对话上下文 + 已有图表 → ReportPlan |

### 4.2 意图路由（对应流程图的分支）

```
用户消息
  ↓
IntentRouter（语义识别）
  ├─ data_query      → 匹配最合适图表 → 公共取数 → 图表卡 + 文字回复（流程图右侧支）
  ├─ report_build    → 自动生成报告提纲 → 确定每页内容 → 选定所需图表 → 公共取数（流程图左侧支）
  ├─ canvas_revision → 只改画布产物（改标题/图表类型/删页），不取数
  ├─ rollback        → 恢复到指定版本
  └─ unknown         → 澄清追问
```

## 5. 数据模型变更

### 5.1 新增

| 模型 | 关键字段 |
|---|---|
| `ConversationDTO` | `conversation_id, session_id, scene_id, status, created_at` |
| `MessageDTO` | `message_id, conversation_id, role(user/assistant/system), content, intent, artifact_refs[], status(streaming/done/failed), created_at` |
| `ArtifactDTO` | `artifact_id, conversation_id, message_id, kind, payload, lineage{query_id, sql, scene_id}, version, created_at` |
| `DimensionCardDTO` | `title, dimension_key, reason, sample_fields[], selected` |
| `ChartCardDTO` | `chart_type, x_field, y_field, series_field, rows[], sql, query_id, table_header` |
| `OutlineCardDTO` | `report_plan_id, pages[{order,title,objective,bound_artifact_id,status}]` |
| `DeckCardDTO` | `deck_id, slide_ids[], current_revision_id, mode(preview/edit)` |
| `WorkingMemoryDTO` | `selected_dimensions[], produced_artifact_ids[], active_outline_id, active_deck_id, brand_locked` |

### 5.2 改造

- `ReportPlanDTO` / `ReportPageDTO`：增加 `conversation_id` 与 `source_artifact_ids[]`（页面能溯源到对话里的那张图）
- `SlideDraftDTO`：增加 `chart_card_id`，使 PPT 页与画布图表卡一一对应
- `QueryRunDTO` / `SlideDraftDTO`：lineage 统一带上 `message_id + artifact_id`

> 设计原则：**画布上的每张卡都是可寻址的 Artifact**，PPT 页 = 引用若干 Artifact。这样"第 4 页换成落地建议""第 1 页标题改短"这类指令才有明确的落点，也天然支持编辑与回退。

## 7. 前端改造方案

### 7.1 版式

```
┌──────────────┬───────────────────────────────────────┐
│ 会话/场景侧栏 │  左：对话流            │ 右：动态画布  │
│ （保留精简）  │  （消息 + 内联引用）    │ （卡片栈）    │
└──────────────┴───────────────────────────────────────┘
配置中心 / 服装检索 → 收进"设置"抽屉，不再是一级 Tab
```

### 7.2 组件清单（新建）

1. **对话流**：气泡、流式打字、进度态（"正在识别意图…正在取数…"）、消息内产物引用（"已生成 2 张图表 ↑"）
2. **画布编排器**：按 `artifact.kind` 分派渲染，新卡片随消息**增量插入 + 过渡动画**，支持置顶/收起/删除
3. **图表卡**：ECharts 封装 + 图表/数据表切换 + SQL 展开
4. **维度标签卡**：可多选，选中后触发取数
5. **大纲编辑器**：页序拖拽、页-图绑定、增删改
6. **PPT 预览/编辑**：16:9 版式渲染、文本原地编辑、翻页、`[导出 .pptx]` / `[复制图片]`

### 7.3 卡片协议（关键设计）

前端主循环只认 `kind` 与通用外壳，新增卡片类型不改主循环：

```json
{
  "artifact_id": "art_xxx",
  "kind": "chart_card | dimension_card | outline_card | deck_card",
  "payload": { "...": "由对应渲染器解释" },
  "lineage": { "message_id": "m1", "query_id": "q1", "sql": "..." },
  "version": 2
}
```

### 7.4 技术决策（需你拍板）

- **D1 前端栈**：继续 no-build（原生 ESM + 组件化 JS）——零构建、易交接、与现状一致；还是引入 Vite + Vue/React——组件化好、但引入构建链与新交接成本。**建议**：M1 先用 no-build + ESM 模块拆分（把 5673 行 main.js 拆成 `chat/` `canvas/` `renderers/`），把"是否上框架"延后到 M3 评估。
- **D2 通信**：REST + **SSE** 流式进度（比轮询体验好、实现成本可控）。
- **D3 场景前置**：改为"对话里自动匹配场景；匹配不到用默认场景；配置中心保留精修"。避免"必须先建场景"的高门槛。
- **D4 HITL 强度**：默认自动推进；关键节点（大纲确认、PPT 生成前）保留确认；全流程保留编辑/回退。

## 8. 关键技术风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 图表与文案不一致 | 前端 ECharts 与 PPTX 图表是两套渲染 | 统一走 `ChartSpecService`，同一份数据派生（复用现有 `ReportChartBindingDTO` 词表） |
| LLM 时延/失败 | 路由与大纲生成依赖 LLM | 沿用现有"规则降级"模式（`planner_mode: rules`） |
| 数据口径漂移 | 对话式容易绕过场景确认 | 复用 `field_value_resolver_service` 消歧；未消歧值禁止执行 |
| 会话恢复 | `VIBE_PERSIST_STATE` 默认关闭 | 打开并补重启续写回归 |
| 范围扩散 | 一旦做对话很容易被要求"什么都支持" | 用 Artifact `kind` 白名单锁死能力边界 |
| 前端重构量大 | 双栏 + 图表 + 编辑器是全新增量 | 分期交付，M1 只做"对话 + 图表卡"最小闭环 |

## 9. 分期计划

### M1：对话流 MVP（约 1–2 周）

目标：**"说一句 Zara → 出维度卡 → 点两个标签 → 出两张图"** 跑通。

1. 新增 `ConversationDTO / MessageDTO / ArtifactDTO` 与 `ConversationService`。
2. 新增 `IntentRouter`（先支持 `data_query` 与 `unknown`）。
3. `sql_result_agent_service` 包装为对话可调用的"公共取数模块"。
4. 新增 `DimensionRecommender` + 维度卡。
5. `ChartSpecService` + 前端 ECharts 图表卡（含 SQL 展开、数据表）。
6. 前端：双栏骨架 + 对话流 + 画布卡片栈（先支持 2 种卡）。

**验收**：第一、二轮对话可完整发生；图表可交互、可看 SQL、可看数据明细。

### M2：报告大纲与 PPT 交付（约 1.5–2 周）

目标：**"把这两张图串成 4 页 PPT → 改第 4 页 → 生成 PPT → 导出"** 跑通。

1. `ReportComposer`：对话上下文 → 大纲；**已出图自动挂载**到页；标注待取数页。
2. 大纲卡编辑器（页序、绑定、增删改）。
3. `IntentRouter` 增加 `report_build` / `canvas_revision` / `rollback`。
4. 大纲缺数据页自动补取数并绑图（复用 `report_workflow` 的页级链路）。
5. PPT 预览/编辑模式（16:9 + 原地改字），导出复用 `report_pptx_export_service`。
6. 打开持久化，做重启续写回归。

**验收**：第三、四轮对话可完整发生；4 页 PPT 可在右侧翻阅、改字、导出 pptx；删页/换页生效。

### M3：打磨与生产化（约 1–2 周）

1. SSE 流式进度与失败重试。
2. `WorkingMemory`：多轮引用（"刚才那张图""第一页"）。
3. lineage 落库：任一张卡/任一页可回溯 message → query → SQL。
4. 模板/主题（封面、目录、来源页）。
5. 回归案例集 + 客户库冒烟。
