# 后端阻塞缺陷：一轮对话把整个服务冻住（修复记录）

日期：2026-10-06
范围：`apps/vibe_backend/app/routers/conversation.py`、`app/services/conversation_service.py`
（**只动新链路**；老配置页的路由一行未改）

---

## 1. 现象

用户在页面上看到「多轮对话服务（DeepFlow agent）当前不可用」，同时发现**整个后端像死了一样**：

```
curl --noproxy '*' --max-time 5 http://127.0.0.1:18900/health
→ 000（超时），连试 3 次都是 000
```

但进程是活的、端口在监听：

```
lsof -nP -iTCP:18900 -sTCP:LISTEN   → Python 49728 LISTEN
```

于是很容易得出两个**错误**结论：
①「后端挂了，重启一下」→ 重启脚本看起来"没用"；
②「是不是别的项目占了我的端口」→ 去找一个不存在的第三方占用。

## 2. 真因

`app/routers/conversation.py` 里所有处理函数都写成了 `async def`，而函数体里直接调用
**同步阻塞**的 `conversation_service.*`：

```python
@router.post("/{conversation_id}/messages")
async def send_message(conversation_id: str, body: SendMessageRequest) -> dict:
    result = conversation_service.handle_message(...)   # ← 同步调用，最长等 LLM 数分钟
```

一轮对话要等 DeepFlow agent（LLM）。**网关缓慢或不可达时，实测卡 227 秒**。
`async def` 的处理函数跑在事件循环上，于是这 227 秒里：

- `/health` 超时（000，不是 500——因为请求根本没被处理，只是排队）；
- 新画布的所有接口一起卡住；
- **老配置页的接口也一起卡住**（同一个事件循环）。

进程完全没有异常、也没有收到过 SIGTERM，**它只是忙**。

## 3. 为什么这个缺陷特别难排

它和「半死残留实例」的症状**完全一样**：

| | 半死残留（SIGTERM 后 socket 还占着） | 忙在等 LLM（本缺陷） |
|---|---|---|
| 端口 | LISTEN | LISTEN |
| `/health` | 000 | 000 |
| `lsof -p <pid>` | 有 `->2124` ESTABLISHED | 同样有 `->2124` ESTABLISHED |
| **等一两分钟** | **永远 000** | **自己恢复 200** |

唯一可靠的区分就是"等一两分钟会不会自己好"。

更糟的是它会造成**误杀**：`scripts/start_vibe_stack.sh` 把「端口在监听 + 健康不通」判为残留并清理。
用户**在对话进行中去双击重启脚本**，就会把一个健康的、只是在等 LLM 的实例 SIGKILL 掉。
（今天真实发生：用户正是先看到提示、再去重启的。）

## 4. 修法

### 4.1 路由改成同步处理函数

```python
# conversation.py 顶部（保留这段说明，别被"顺手改成 async"）
# 本文件的路由处理函数一律写成同步 `def`，不要改成 `async def`：
# 函数体里调用的 conversation_service.* 都是同步阻塞的……
# 写成同步 `def` 后 Starlette 会自动把它丢进线程池，事件循环保持空闲、其他接口照常响应；
# 会话状态的一致性由 ConversationService._turn_lock 保证。
```

处理函数由 `async def` 改为 `def`（22 个）。FastAPI/Starlette 正是按「处理函数是不是协程」
决定走线程池还是事件循环，所以这一处改动就够。

### 4.2 把"同一时刻只处理一轮"的语义显式保住

从前所有处理函数都在事件循环上，天然串行；改成线程池后可能真的并发进来，
而会话状态是进程内的全局字典（`store.CONVERSATIONS` / `MESSAGES` / `ARTIFACTS`），本身没有锁。
所以把入口一拆为二：

```python
class ConversationService:
    _turn_lock = threading.RLock()      # 保住"同一时刻只处理一轮"的原有语义

    def handle_message(self, *, conversation_id, text, selected_dimension_keys=None, scene_id=None):
        """公开入口：串行化之后交给 _handle_turn 干活。"""
        with self._turn_lock:
            return self._handle_turn(...)

    def _handle_turn(self, *, ...):     # 原来的实现体，一行未改
        ...
```

签名不变，调用方（路由、测试）都不用改。

## 5. 验证

**实测**（在途对话正卡着等 agent 的同一时刻）：

```
lsof -p <pid>  →  58965->127.0.0.1:2124 (ESTABLISHED)     ← 确实还在等
curl /health                                  → 200 t=0.0007s
curl /api/v1/conversations                    → 200 t=0.0020s
curl /api/v1/clothing/items?limit=2（老页）    → 200 t=0.3268s
curl /api/v1/scenes                           → 200 t=0.0795s
```

修复前，同样状态下这四个都是 **000**。

**守卫测试** `apps/vibe_backend/tests/test_conversation_route_blocking.py`：

- 源码级：`conversation.py` 里不许出现 `^async def`，也不许出现 `await`
- 长阻塞处理函数（`send_message` / `apply_artifact_action` / `build_outline` / `regenerate_outline_page` /
  `fill_pending_pages` / `compile_outline` / `execute_chart_sql` …）逐个断言**不是协程函数**
- `_turn_lock` 存在且可重入
- 公开入口确实 `with self._turn_lock:` 并转调 `_handle_turn`
- **三个线程并发跑轮次，同一时刻在执行体的最多只能有 1 个**（打桩 LLM 依赖，不伪造业务数据）

单测：106 → **118 passed**；`bash scripts/verify_canvas_all.sh` 全绿。

## 6. 与本次「配置按需加载」的关系

无关，是独立缺陷：**只要一轮对话在等 LLM，就会触发**，与配置按需加载无关。
它是在排查"页面提示服务不可用"时顺带发现的。

## 7. 还没解决的部分（环境）

页面提示「多轮对话服务当前不可用」的**直接原因**是内网大模型网关不可达：

```
nc -z 20.255.59.22 4000  → TCP FAIL      443 → TCP FAIL
curl（走代理）            → 502
curl github.com / baidu  → 通
```

公网能通**不代表**内网网关能通——两者是完全不同的网络路径。
`deploy/fz-workflow-demo.app.env` 与 deer-flow `config.yaml` 指向同一个网关，
所以**新画布与老配置页的取数此刻都会失败**（本轮改动没引入这个问题）。
连上对应网络/VPN 后即可恢复；届时按
