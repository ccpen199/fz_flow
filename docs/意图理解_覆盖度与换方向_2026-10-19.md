# 意图理解：覆盖度问题要直接回答，「换个方向」要真的换（2026-10-19）

> 用户三连问的截图：
> 1. 「你看看优衣库在哪个月份有数据」→ 弹出「优衣库 4 个候选，选一个」；
> 2. 「你好」→ 回复仍绕着那张待确认卡；
> 3. 「换个方向」→ 还是那批东西。
>
> 原话：「agent根本不理解我在问什么。没法理解任务」「我说了换个方向 它还是继续在原来的方向去打转」
> 「你不要乱改代码。首先最起初的功能有问题。」

## 1. 诊断：agent 其实听懂了，是后端接不住

把三轮的 **agent 原始判定**打出来（`_plan_turn_with_agent` 的返回）：

| 轮次 | agent 的 intent | agent 的话 | 关键字段 |
| --- | --- | --- | --- |
| 「哪个月份有数据」 | `data_query` | 「好，我按月份来看优衣库的数据覆盖情况」 | `dimension_keys: []` 或 `["trend"]`、`filters:[品牌=优衣库]` |
| 「你好」 | `chat` | 「你好，画布上还有个优衣库候选卡…」 | `needs_clarification: true` |
| 「换个方向」 | `explore` | 「可以，趋势这条先放一边」 | `dimension_keys: []` |

**结论：不是模型听不懂，是判定的结果没有对应的执行路径。**

- `dimension_keys` 是**预设方向**（纤维/色彩/趋势/价格带…）的闭集，没有「看数据覆盖」这个方向 →
  agent 只能返回空。空方向落到分支：
  - `not picked_keys and (chart_type or filters)` → 走「只改口径」（"画布上还没有图表…"）；
  - `not picked_keys` → 把 agent 那句承诺**当回答发出去**，用户等不到任何数据；
  - 若关键词路由补了个 `trend` → 走进取数 → 撞上品牌 4 候选 → 弹消歧卡。
- 「换个方向」没有动作语义：只能让 agent 回一句话，画布不变、待确认卡还挂着 →
  用户看到的就是"原地打转"。

## 2. 改动（两处，都在分派层，不碰取数 SQL）

### 2.1 覆盖度问题：直接答，不选品牌、不选方向

- `intent_router.is_coverage_question()`：识别「哪个月份有数据 / 有数据的月份 / 覆盖到什么时候 /
  有哪几个月」。**句式刻意收紧**，不吞「哪个月份销量最高」这类真取数问题。
- `_monthly_coverage(scene, values)`：一条只读 SQL
  `品牌 × 月份 → COUNT(DISTINCT Id)`；表列白名单、参数化执行、**卡片里存字面量 SQL**
  （`verify_canvas_all.sh` 会拿它回 MySQL 逐值复算）。
- `_answer_coverage_question()`：品牌多候选时**逐个口径统计**（不合并、不猜），
  回复直接给每个口径的月份区间/条数，画布出一张「月度数据覆盖」折线（x=月份，series=品牌）。
- 入口放在 `_handle_turn` 分派链**最前面**：否则会被"只改口径/选方向/选品牌"任一条截走。

### 2.2 「换个方向」= 放弃上一个问题

- `_wants_direction_switch()`：只认明确换向说法（换个方向/换一个角度/先不选品牌/看点别的）。
- `_retire_pending_resolution()`：把仍处于 `needs_confirmation` 的消歧卡从画布撤下，
  并在回复里明说「之前那张选品牌卡已撤下」。**品牌槽位本身不动**（真取数时该问还会问）。

- 覆盖度识别仍是**句式规则**，不是 agent 的任务类型。换个说法（如「每个月各有多少条」）

## 5. 补上任务类型契约（2026-10-19 第二轮，用户确认的目标）

用户原话：**「我要你接入 deepflow agent 也是要能够处理用户提出的各种问题的场景。
而不是固定流程的给我取数。」**

上一轮（§1~§4）只是**在分派层打补丁**：用正则认出"哪个月份有数据"，再绕到覆盖度分支。
根因没动——`fz-canvas` 的 `intent` 枚举里**根本没有"问问题"这一类**，`dimension_keys`
又是个闭集，所以 agent 只能把这类问句硬塞进 `data_query + trend`：

```
改动前（真实探测）：
输入「你看看优衣库在哪个月份有数据」
→ {"intent": "data_query", "dimension_keys": ["trend"],
   "config_keys": ["scene_prd_trend"],
   "filters": [{"field": "品牌", "value": "优衣库"}],
   "reply": "好，我按抓取日期看一下优衣库的数据覆盖在哪些月份"}
   ↑ 嘴上完全理解，结构化字段却是"去取一张趋势图"
```

### 契约新增两个任务类型

`deer-flow/backend/.deer-flow/agents/fz-canvas/SOUL.md`：

| 任务类型 | 语义 | 结构化槽位 | 后端动作 |
|---|---|---|---|
| `coverage` | 问**数据本身**：哪个月份有数据 / 数据到什么时候 | `{"kind":"months","brands":["优衣库"]}` | 按品牌口径统计月份，直接给文字 + 覆盖度图 |
| `control` | **只**处置当前话题：换方向 / 先不选了 / 算了 | `{"action":"switch_direction\|drop_question"}` | 撤下待确认卡，不重新出方向卡，不取数 |

关键取舍：
- **`coverage` 不填 `config_keys`**。覆盖度读的是事实表全局时间列，跟哪套配置的指标无关；
  硬挑一套就是猜（头部说明相应改成「覆盖度按全库事实表统计，不依赖单一配置」）。
- **`coverage` 不填 `dimension_keys`**。填任何一个 key，后端就会去取图 —— 那正是答非所问。
- **`control` 不许判成 `explore`**。`explore` 会拿会话品牌重渲染一张「X 分析切入点」，
  用户看到同一品牌同一批入口 = 原地打转。
- 带了新方向的「先不选品牌了，看看价格带」→ 仍是 `data_query`，不是 `control`。

### 后端只做执行，不再用正则猜

- `deepflow_agent_service.VALID_INTENTS` 放行两个新值，`coverage` / `control` 作为
  **对象槽位原样回传**（形状不对就当没填，绝不让下游 `.get()` 崩）。
- `_handle_turn` 分派链最前面判 `asks_coverage = (intent == coverage or 规则命中)`，
  `intent == control` 走 `_handle_control`。**规则命中降级为兜底**：agent 偶尔仍判成
  `data_query + trend` 时，那条兜底还能救回来。
- 覆盖度要统计谁：`_coverage_subjects()` 的优先级是
  **agent 槽位里的品牌原话 → 它写的品牌筛选 → 会话品牌**。
  一个都没给 = 全库（「这批数据到什么时候」）；**点名了却解析不出来 = 如实说，不许放大成全库**。

### 顺手修掉的一个真 bug（全库覆盖度）

无品牌那条 SQL 原来用了**带参数版本**（`DATE_FORMAT(...,'%%Y-%%m')`）。没有参数时
pymysql **不做 % 插值**，`%%Y-%%m` 原样送进 MySQL，整列月份变成字面量 `"%Y-%m"`：
页面显示「共 1 个月（97879 条记录）」。改为无参数时执行单 `%` 的那一版，并加回归
`test_global_coverage_sql_uses_single_percent_when_there_are_no_params`。

## 6. 续：对比（compare）、解释（explain）、下钻分组（group_by）

上表里那句话——「agent 其实听懂了，是后端接不住」——在这三类问法上**又重演了一遍**：

| 用户原话 | 修复前 agent 的判定 | 修复前的实际结果 |
| --- | --- | --- |
| ZARA和优衣库对比一下价格带 | `data_query`，`filters: []`（主体只写进 reply） | 只查了会话里那一家，用户以为是两家在比 |
| 为什么优衣库中国这个月是0 | `coverage`（`brands: ["优衣库中国"]`） | 去统计月份覆盖，答非所问 |
| T恤里再按颜色拆一下 | `data_query`，`dimension_keys: ["structure"]`，`filters:[二级类目=T恤]` | 判对了条件，但**分组列没地方放** → 照旧画 `一级类目`，rows=1 |

### 6.1 契约：三个新槽位

`SOUL.md` 的 `intent` 枚举补 `compare` / `explain`，输出对象补 `compare` / `explain` / `group_by`：

```json
"compare": {"subjects": ["ZARA", "优衣库"]},
"explain": {"about": "number"},
"group_by": ["颜色"]
```

语义边界写死在契约里（这三组最容易判混）：

- `compare` = **两个以上主体放在同一口径下比**。"优衣库价格带怎么样"只有一家 → `data_query`。
  主体**不许**写进 `filters`（否则后端会把 `品牌 ∈ A/B` 对齐成 `= 某一个`）。
- `explain` = 对**画布上已有结果**追问/质询。**不是** `coverage`（问有没有数据），
  也**不是** `data_query`（再取一遍）。`about` 只有 `number / method / empty`。
- `group_by` = **在已有范围里换个字段拆开看**，是"分组的列"，不是新的分析方向：
  `dimension_keys` 决定指标口径，`group_by` 只决定按什么拆。字段名必须真实存在且可分组。

### 6.2 后端：只加"分派 + 校验"，不动取数 SQL

- `deepflow_agent_service`：`VALID_INTENTS` 放行两个新意图；`compare` / `explain` 作为对象槽位、
  `group_by` 作为字符串列表**原样回传**（形状不对就当没填）。字段/配置是否真实，
  一律交给对话层用**本轮实际加载的配置**校验——这一层看不到配置，不许猜。
- `_handle_compare`：把点名的主体用**标准品牌字典**解析，压成**一条** `品牌 ∈ A / B` 条件，
  再走一次 `_handle_data_query(compare_values=…)`。取一次数、一条 SQL、按品牌分组 ——
  不是"各查一遍拼两张卡"（拼卡就无法逐值复核，并排也更难读）。
  - 一个品牌名对应多个口径（优衣库 4 个）→ **全部放进对比**并说明，不替用户挑一个；
  - 只落成一个主体 → 按单品牌取数，但**明说**"这不是对比"；
  - 结果没按品牌拆开 → 明说"这不是对比"，不拿合计数冒充。
- `_handle_explain`：**只读卡片**（`applied_filters` / `time_window` / `rows_count` /
  `findings` / `sql_explanation` / `error_detail`），不重新取数、不推算数字。
  画布上没有数据卡时，先看有没有**待确认卡**（`needs_confirmation` 与 `needs_clarification`
  两种都认），把那张卡记下的查库证据讲清楚。
- `_resolve_group_by`：只接受本轮配置里 `role ∈ {dimension, filter}` 的字段；
  指标/时间/不存在的列一律如实退回（时间要按日期粒度截断，那是趋势方向的口径）。
  `_execute_goals` 里把目标改写成"按 X 分组，每组一行，不要按其他维度分组"，
  同时把回复里的"已聚合 一级类目 与 价格"改成"已按 颜色 拆分、统计 价格"。

### 6.4 踩到的两个坑（都值得记住）

1. **"给 agent 看的方向" ≠ "落卡用的方向"。**
   下钻时 agent 必须看见**平台总共能服务哪些方向**（卡片 ∪ 合并视图），否则它以为没有
   "色彩"这个方向，只好硬套旧方向。但**落卡**必须只用**本轮配置**推出来的方向。
   一开始把两者合在同一个 `options` 变量里，直接踩了守卫
   `test_dimension_card_is_built_from_the_turn_config_not_the_merged_view`（`assert 3 == 2`）。
   现在合并视图走带缓存的 `_overview_dimension_options()`，落卡仍走 `_ensure_dimension_options()`。
2. **`Decimal` 不是 `float`。** `_zero_evidence` 原来只判 `isinstance(x, (int, float))`，
   pymysql 的 `DECIMAL` 全被漏掉 → "为什么这个月是 0"永远拿不到"这张卡里其实没有 0"。
   新增 `_as_number()` 统一转 float（`Decimal` / 数字字符串都认）。

### 6.6 充值后实测又修的三处（同一晚）

DeepSeek 账户充值后（余额 9.99，`/probe` 200 / 1092ms）跑真链路，暴露了三件事：

1. **`explain.about` 判对了却没用上**：「这个数怎么算出来的」和「为什么这个月是 0」回的是同一段话
   （结论 + "没有 0" 一起堆上来）。现在 `_handle_explain` 按 `about` **裁剪**：
   - `method` → 只给口径说明 + SQL，不堆结论、不谈"有没有 0"；
   - `number` → 结论依据 + "这张卡里到底有没有 0"；
   - `empty` → 优先解释**没出结果的那张卡**（失败的图 > 待确认卡），
     不再去解释画布上更早、跟这句话无关的旧图。
   口径行里补了「按什么分组 / 指标是什么」——用户问"这个月为什么是 0"时，
   一眼能看出这张卡根本没按月拆。
2. **标准值没命中只说引擎术语**：「只看女装」被闸门拦下，回复是
   "SQL Agent 生成了当前数据库无法命中的标准值过滤"，用户不知道下一句说什么。
   现在失败时用 `empty_result_diagnosis_service` 数一遍该字段在**这批人群**里的真实取值：
   > 「适用性别 =女装」在库里没有这个取值，所以没有出图；这批数据里实际是
   > 「女」、「通用」、「男」。换成其中一个我就按新口径重跑。
   品牌作为固定条件参与计数、不进"可换掉"的候选池；找不到正向证据就**不说话**（不猜）。
3. **"女装"会被塞进类目字段**：实测 3 次里有 1 次判成 `一级类目 = 女装`（库里没这个类目值），
   条件静默落不到 SQL。契约补了一条：**人群/性别限定（女装/男装/童装/情侣款）说的是「适用性别」
   这类人群属性字段，不要塞进类目**。改后连跑 3 次都稳定落到 `适用性别`。
