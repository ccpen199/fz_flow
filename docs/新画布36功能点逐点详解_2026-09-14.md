## 先看一张图：一句话进来，经过哪 7 层

```
你的一句话
   ↓ L0 入口层       会话 + 消息通道（4 个功能点）
   ↓ L1 解析层       定字段口径：用哪个场景、抽时间窗与页数（4）
   ↓ L2 路由层       这句话想干什么：5 类意图打分（5）
   ↓ L3 分派层       按意图走 5 个分支之一（5）
   ↓ ── 只有 data_query 继续往下 ──
   ↓ L4 执行层       消歧 → 编排 → 并行取数 → 两道 SQL 闸门 → 图表规格 → 澄清（9）
   ↓ L5 落卡层       产物写进画布、升版本、可回退、可装配 PPT（6）
   ↓ L6 呈现层       前端按 kind 分派渲染（4）
画布上出现可寻址的产物卡
```

三道人工关卡分别卡在 **L4 入口（消歧）**、**L4 出口（澄清）**、**L5 中段（参数抽屉）**——这就是"多轮"的来源。

# L0 入口层 · 会话与消息（F0.1–F0.4）

## F0.1 创建会话 `create()`

- **做什么**：给一个分析会话发号，并同时初始化"场景"和"工作记忆"两样东西。工作记忆是后续所有轮次的上下文载体。
- **什么时候触发**：前端发现 `state.cid` 为空时自动建。也就是你**第一次开口时**，不需要点"新建会话"。
- **内部怎么做**：
  - `POST /api/v1/conversations` → `ConversationService.create()`
  - `conversation_id = f"conv_{uuid4().hex[:10]}"` —— 这就是 `conv_96ed342a28` 这种 id 的来路，**是随机发号，不含业务含义**。
  - 标题：优先用传入的 `title`，为空则用 `f"{scene.name}会话"`。
  - **场景在这一步就解析了**：`resolve_scene(text=seed_text or title)`，并记 `working_memory.scene_locked_by = "explicit" | "auto"`。
  - 前端把 id 写进 `localStorage["fz_agent_cid"]`，刷新页面能接着聊。
- **实测例子**：`conv_96ed342a28`｜标题「验收·Zara复盘」｜`scene_id=scene_prd_competitor`｜`scene_locked_by=auto`｜`brand=ZARA`。
- **代码**：`conversation_service.py:105`（create）· `agent.js:311`（`if (!state.cid) return createConversation().then(...)`）· `agent.js:1085`
- **边界**：没有可用场景时 `scene_id=None`，后续会走 F1.2 的明确失败，而不是硬跑。

## F0.2 发送消息 `send()`

- **做什么**：把一句话（可附带在维度卡上点选的 key 列表）投给后端；本地先插一条用户气泡让界面立刻有反馈，等后端返回后用服务端结果整体刷新右栏。
- **什么时候触发**：点发送按钮、输入框回车、或点维度卡的「看选中的维度」。
- **内部怎么做**：
  - 前置守卫：`if (state.busy) return;` —— 忙的时候重复点发送**直接丢弃**。
  - `setBusy(true, keys.length ? "正在取数并出图（约 15 秒）…" : "正在识别意图…")`，`setBusy` 会 `$("sendBtn").disabled = busy`。
  - 本地插入用户气泡（带维度时后缀「（已选维度：fiber,price）」）。
  - `POST /api/v1/conversations/{id}/messages`，body = `{ text, selected_dimension_keys }`；**没打字的点选**会发文本 `"看这些维度"`。
  - 返回后：`state.canvas = res.canvas` → 清空选中 → `refreshDetail()`。
- **实测例子**：点选「面料成分」+「价格带」→ 实际发送 `selected_dimension_keys:["fiber","price"]`。这个 key 列表在 L2 会让 `data_query` **无条件 +4 分**，所以点选一定会走取数，不会被误判成"探索"。
- **代码**：`agent.js:308`
- **边界**：请求失败时插一条 `role:"system"` 消息「本次请求失败：…」，不静默丢弃。

## F0.3 加载会话 / 画布

- **做什么**：**一次请求同时拿回消息列表和画布**，避免左右两栏分别请求造成闪动和不同步。
- **什么时候触发**：`boot()` 时；以及每次画布动作成功后（`refreshDetail()`）。
- **内部怎么做**：`GET /api/v1/conversations/{id}` 返回 `{ conversation, messages, canvas }`。`boot()` 的顺序是：`GET /health` → `loadConversations(savedCid)`（找回上次的会话）→ `loadConversation(id)`。
- **实测例子**：打开 `conv_96ed342a28` 一次拿到 **12 条消息 + 5 个产物**。
- **代码**：`agent.js:1024`（loadConversation）· `agent.js:1150`（boot）
- **边界**：`localStorage` 里的 cid 失效时，`loadConversations` 会退回最近一条会话，不会白屏。

## F0.4 健康检查

- **做什么**：启动先探一次后端。探不通就在**对话流里**明说"无法连接后端 …，请先启动后端服务"，而不是让你对着白屏猜。
- **什么时候触发**：每次 `boot()`，在拉会话之前。
- **实测例子**：`GET /health` → `{"status":"ok","service":"vibe-backend","phase":"persistent-skeleton"}`。
- **代码**：`agent.js:1173`
- **边界**：探活失败后流程仍会继续走 `loadConversations`（catch 返回 `null`，`then` 照常接着跑），所以你仍能看到历史会话——只是新消息会失败。

# L1 解析层 · 场景与字段语义（F1.1–F1.4）

> 这一层决定"这次用哪套字段口径"。它是后面所有取数的前提——同一句"价格带分布"，在不同场景里查的是不同的表、不同的字段。

## F1.1 场景解析 `resolve_scene`

- **做什么**：把"这次分析该用哪个场景"定下来。场景 = 一组启用的表 + 字段 + 语义名（例如 `scene_prd_competitor` = 竞品与价格分析）。
- **什么时候触发**（**这是最容易理解错的一点**）：
  - 建会话时用 `seed_text or title` 解析一次；
  - 之后**只有两种情况会重算**：① HTTP 显式传了 `scene_id`；② 会话还没有 `scene_id`。
  - **其余一律沿用会话已锁定的场景** —— `handle_message` 里是 `if scene_id or conversation.scene_id is None:` 才调 `resolve_scene`。
  - 所以：**场景一旦锁定，整段会话都用同一套口径**，后面问什么都不会换。
- **内部怎么做**（三级判定）：
  1. 显式 `scene_id` → `scene_cache_service.get_scene(id)`，拿到即返回。
  2. 按 `SCENE_ROUTING_HINTS` **5 组提示词**打分：每个提示词命中 **+2**；再遍历该场景的 `sample_goals`，其前两个词命中再 **+1**。择优条件是 `score > best[0]` —— **严格大于才替换，所以同分取列表中最靠前的那个**。
  3. 全部零分 → 用默认场景 `DEFAULT_SCENE_ID = "scene_prd_competitor"`；若连它也没有，取第一个有字段的场景。
- **实测例子**（`resolve_scene` 真实返回）：
  | 输入 | 命中明细 | 结果 |
  |---|---|---|
  | 「最近想复盘一下 Zara，帮我分析看看」 | **5 组全零命中** | 走第 3 级**默认兜底** → `scene_prd_competitor` |
  | 「先看近 5 个月的纤维混纺和价格带，出图直观点」 | competitor(价格)=2、price(价格带)=2、scene_0004(纤维)=2 **三组同分** | 取列表靠前者 → `scene_prd_competitor` |
  | 「The North Face 最近30天…价格带分布」（直接调用时） | structure(类目)=2、competitor(价格)=2、price(价格带)=2 **同分** | 取靠前者 → `scene_prd_structure` |
  | 「看看上新节奏和爆款」 | trend 命中「上新」「节奏」「爆款」= **6 分** | `scene_prd_trend` |
- **代码**：`conversation_service.py:81`（resolve_scene）· `:40`（SCENE_ROUTING_HINTS）· `:103`（默认兜底）
- **边界**：所有场景都零字段时返回 `None` → F1.2。
- **⚠️ 勘误**：本手册 v1 曾写"「最近想复盘一下 Zara…」命中「价格」「品牌」「竞品」→ 选 competitor"，**这是错的**。该句全零命中，走的是默认兜底。已修正。

## F1.2 无场景时明确失败

- **做什么**：一个场景都取不到时**不猜、不硬跑**，回一条用户能照着做的提示，并把这条消息标成 `intent=unknown`、`status=failed`。
- **什么时候触发**：`resolve_scene` 三级全返回 `None`。
- **内部怎么做**：`handle_message` 在 `scene is None` 时直接落一条助手消息，`error="scene_not_found"`，然后 `persist_state()` 返回——**不再往下走路由**。
- **实测文案**：「当前没有可用的场景配置。请先在配置中心创建或同步场景，再回来继续对话。」
- **代码**：`conversation_service.py`（handle_message 内 `scene is None` 分支）· 文案与 `intent=INTENT_UNKNOWN`
- **边界**：这是"宁可明说不可猜"的一个实例，和 F4.2 消歧卡是同一个设计原则。

## F1.3 维度资产 `_ensure_dimension_options`

- **做什么**：把场景里 `enabled` 的字段语义，按 **6 个主题**（面料成分/价格带/流行色彩/品类结构/品牌竞争/上新节奏）推荐成"切入点"，落成一张 `dimension_card` 让你点选。
- **什么时候触发**：`explore` 分支直接建；`data_query` 与 `_execute_goals` 每次也会调一次做**保底**（没有卡就补一张）。
- **内部怎么做**：
  - 先查缓存：若已有 `dimension_card` 且 `payload.brand` 与当前品牌**一致** → 直接用缓存 `options`，不发任何请求。
  - 品牌**变了** → 重新 `recommend()` 并**原地覆盖同一张卡**，且 `push_version=False`（**不升版本**，因为还是同一张卡，只是刷新）。
  - 每个 option 的结构：`dimension_key / title / angle / keywords / prefer_metrics / prefer_dimensions / match_terms / chart_hint / reason`。
  - 标题 `f"{brand or ''}分析切入点"`，副标题 `f"基于 {scene.name} 的字段资产推荐"`。
  - 每张卡最多 `MAX_FIELDS_PER_CARD = 6` 个字段。
- **实测例子**：ZARA → 产物 `art_9128a56dd2`「**ZARA分析切入点**」，副标题「基于 **竞品与价格分析** 的字段资产推荐」，4 个切入点：面料成分与纤维混纺 / 价格带与折扣节奏 / 品牌竞争格局 / 流行色彩矩阵。
- **代码**：`conversation_service.py:763` · `dimension_recommender.py:165`（recommend）· `:13`（THEMES 6 组）· `:85`
- **边界**：`recommend()` 返回空 → 返回 `[]`，后续取数会因"没有维度"只回文案不取数。

## F1.4 时间窗与页数抽取

- **做什么**：从句子里抽出**时间窗**与**页数**，分别供取数和汇报使用。
- **什么时候触发**：每条消息（在 `route()` 内部总会执行）。
- **内部怎么做**：
  - `extract_time_window(raw)`：**6 条正则**（`近/最近 N 天·周·月`），返回规范化文本，如 `近5个月`。注意它填的是 `近`，不是 `最近`。
  - 页数：`PAGE_COUNT_PATTERN = (\d+)\s*页`，然后**夹到 2–12 页**，防止"串个 100 页"。
  - 页码另有一套：`PAGE_INDEX_PATTERN = 第\s*(\d+)\s*页` + 中文序数表 `CN_PAGE_INDEX`（第一页…第七页）。
- **实测例子**：「先看**近5个月**的纤维混纺…」→ `time_window="近5个月"`；「The North Face **最近30天**…」→ `time_window="近30天"`；「帮我串个 **4 页**左右…」→ `page_count=4`。
- **代码**：`dimension_recommender.py:282`（extract_time_window，6 条 TIME_PATTERNS）· `intent_router.py:53`（两个正则）· `:160`（_extract_page_count）
- **边界**：只认"数字+页"。**「第四页」是页码不是页数**——它会走 `CN_PAGE_INDEX` 变成 `page_index=4`，用于 F3.4 换页。

# L2 路由层 · `IntentRouter.route`（F2.1–F2.5）

> 纯规则、离线、可审计，**不调 LLM**。文档注释里写明了理由：模型慢或不可用时，这条链路仍然要给出确定的结果。同一套规则顺手抽三个槽位：品牌、页数、时间窗。

## F2.0 意图判定改走 DeepFlow 多轮 agent（2026-09-15 新增）

- **做什么**：意图不再由关键词打分决定，而是把「用户原话 + 场景 + 品牌记忆 + 画布已有维度 + 真实维度清单」交给 deer-flow 的 LangGraph agent `fz-canvas`（`127.0.0.1:2124`，模型 `fz-gpt-5.2` 走内网网关），拿回严格 JSON。
- **契约**：`{intent, dimension_keys, time_window, page_count, reply, needs_clarification, clarify_question}`。
- **后端三道校验**：① intent 不在白名单 → `unknown`；② `dimension_keys` 必须命中真实维度 key，否则丢弃；`data_query` 无有效 key → 追问、不出卡；③ 解析不出 JSON → `unknown` + 追问（`parse_failed=true`）。
- **不兜底**：agent 不可用 → `intent=unknown` + `status=failed` + 明确文案，**不退回关键词猜意图**；`VIBE_LLM_ROUTER=0` 可临时关闭。
- **thread 映射**：`uuid5(固定命名空间, "fz-"+conversation_id)` —— LangGraph 只接受 UUID 形式 thread id；同一会话稳定同一 thread，跨重启靠 checkpointer。
- **实测**：`conv_99bc6bd790` 四轮 —— 你好→`chat`(0 卡) / 看看ZARA的价格带分布→`data_query`+price(出真图卡) / 把已有图表串成一份4页汇报→`report_build`+4 页大纲 / 还有哪些分析方向→`explore`。
- **代码**：`conversation_service.py:_plan_turn_with_agent` · `services/deepflow_agent_service.py` · `docs/DeepFlow多轮对话接入_2026-09-15.md`

> 下面 F2.1~F2.5 描述的是**规则路由**机制。它仍在链路里，但职责已变为：为品牌/页码/时间窗提供槽位与证据，并在规则侧标记 `unknown`；**不再单独决定 intent**。

## F2.1 关键词加权打分

- **做什么**：5 组词表 × 命中数 × 权重 = 各意图得分。
- **什么时候触发**：每条消息。
- **内部怎么做**：
  - 命中判定 `_hits(text, KEYWORDS)` 是**子串包含**（`keyword in text`），且**不去重** —— 所以**子串会重复计分**。
  - 权重：回退 ×3、汇报 ×3、改画布 ×2、取数 ×1、探索 ×1。
  - **点选维度或句子命中维度标题 → 取数 +4**（`_match_dimensions` 只用主题自己的词表匹配，避免共享指标词误命中）。
  - 特殊规则：句中有「分析」但取数得 0 且无点选/匹配 → 探索 **+1**（"帮我分析看看"是探索，不是取数）。
  - 词表规模（实测）：**回退 6 / 汇报 15 / 改画布 28 / 取数 30 / 探索 9 = 88 个**。
- **实测例子**：
  | 输入 | 得分 | 意图 |
  |---|---|---|
  | 最近想复盘一下 Zara，帮我分析看看 | explore **3**（复盘/分析看看/看看）· data_query 1（看看） | `explore` |
  | 先看近5个月的纤维混纺和价格带，出图直观点 | data_query **3**（出图/价格带/图） | `data_query` |
  | 帮我串个4页左右的PPT汇报思路 | report_build **9**＝「串个」「ppt」「汇报」3 词 ×3 | `report_build` |
  | 回退一下 | rollback **3** | `rollback` |
  | 价格带再看一眼 | data_query **1**（价格带） | `data_query` |
  | The North Face 最近30天在各二级类目下的价格带分布 | data_query **2**（价格带/看? ） | `data_query` |
- **代码**：`intent_router.py:85`（打分）· `:59`（`_hits`）
- **边界**：**全靠中文关键词**。换同义词、英文、口语说法会漏判 → 零命中时落 `unknown`，由 F1.6 澄清分支追问（**2026-09-14 晚已按用户要求移除兜底**，见 F2.3）。

## F2.2 同分裁决（硬优先级）

- **做什么**：多个意图**同分**时，按固定顺序取先者：`rollback > report_build > canvas_revision > data_query > explore`。
- **什么时候触发**：**仅当最高分并列**。
- **内部怎么做**：`for candidate in INTENT_PRIORITY: if scores[candidate] > best:` —— **严格大于**才替换。所以这个顺序的真实作用是**同分裁决，压不过更高分**。
- **实测例子（与代码注释不一致）**：「色彩不要了，直接生成 PPT」→ 改画布 **4**（「不要了」+「不要」两个词同时命中同一句，**被子串重复计分**）vs 汇报 **3** → **改画布胜出**，走删页分支，**不会生成 PPT**。而 `intent_router.py:18` 的注释声称 "the build request must win"。**注释与行为不符**，属真实边界；改动会变更行为，**未擅自改**。
- **代码**：`intent_router.py:20`（常量）· `:99`（裁决循环）
- **边界**：只有同分才用得上它，所以日常很少被触发（上面那个例子就没触发）。

## F2.3 零命中 → unknown 追问（兜底已移除）

- **做什么**：一个关键词都没命中时**不猜意图、不出画布卡**，返回 `unknown`，由对话层继续聊天追问，直到用户说出明确目标。
- **什么时候触发**：`best == 0`。
- **内部怎么做**：`intent = INTENT_UNKNOWN`（`intent_router.py:102-108`）。`conversation_service._ask_intent_clarification` 用 `dimension_recommender.recommend`（纯函数、**不落卡**）列出当前场景真实可切入的方向，逐条写进追问文本。
- **实测例子（2026-09-14 22:59 真实接口）**：发「你好」→ `intent: unknown`，画布 **0 张卡**，回复「我还不太确定你这句想做什么……当前场景可切入的方向：面料成分与纤维混纺、价格带与折扣节奏、品牌竞争格局、流行色彩矩阵。你想先看哪个？」
- **历史**：v1 行为是 `explore if not has_charts else data_query` 兜底（「你好」立刻糊一脸切入卡）。**2026-09-14 用户明确要求"不允许有兜底"，已移除**。
- **代码**：`intent_router.py:102-108` · `conversation_service.py:_ask_intent_clarification`
- **边界**：追问只给文字，不给卡；用户说「有什么分析维度」仍可显式触发 explore 拿切入卡。
- **同类兜底一并移除**：`_handle_data_query` 里「没匹配到维度就自动取前两个维度跑」也删了——现在会追问「你想看哪个方向」并指向右侧切入卡（实测「帮我看看数」→ data_query + 追问文本、画布 0 卡）。

## F2.4 槽位抽取（品牌 / 页码 / 时间窗）

- **做什么**：一句里同时抽出品牌、页码、时间窗三个槽位。
- **什么时候触发**：每条消息。
- **内部怎么做**：
  - `_extract_brand`：先在场景的品牌字段上匹配，再查 **28 个种子品牌**（含 `thenorthface` / `the north face` 等变体），并把 ASCII 词形**统一成大写**；同时**排除** `ppt / sql / sku / top / ok / card` 这类会误命中的词。
  - `_extract_page_index`：`第 N 页` 或中文序数。
  - 时间窗：同 F1.4。
- **实测例子**：「The North Face 最近30天在各二级类目下的价格带分布」→ `brand="THE NORTH FACE"`（**大写归一**）、`time_window="近30天"`。
- **代码**：`intent_router.py:146`（_extract_brand）· `:171`（_extract_page_index）· `:53`
- **边界**：种子表外的品牌抽不出来 → 靠 F2.5 记忆，或让你把品牌说清楚。

## F2.5 品牌记忆

- **做什么**：本轮没提品牌，就沿用上一轮的。
- **什么时候触发**：`_extract_brand` 返回空。
- **内部怎么做**：`brand = self._extract_brand(raw, scene) or memory_brand`；`memory_brand` 取 `conversation.working_memory.brand`。抽到新品牌后由 `handle_message` 写回 `working_memory.brand`。

- **代码**：`intent_router.py:99` · `conversation_service.py`（handle_message 内写回）
- **边界**：品牌槽位是**覆盖**语义（对）；但 **goal 文本是拼接**语义，两者不一致——这正是**缺陷 B** 的来路（`THE NORTH FACE ZARA 各二级类目的价格分布情况`）。

# L3 分派层 · 5 个分支（F3.1–F3.5）

> `handle_message` 拿到 `intent` 后走 5 个分支之一，每个分支有自己的处理器和产物类型。**只有 `data_query` 会进入 L4 执行层。**

## F3.1 `explore` → `_handle_explore`

- **做什么**：**不取数**，只把切入点落成一张维度卡让你点选。
- **什么时候触发**：`intent == explore`（含零命中且画布为空）。
- **内部怎么做**：`_ensure_dimension_options` 拿到推荐 → `canvas_orchestrator.plan_explore` 生成引导文案 → `_upsert_artifact(kind="dimension_card", dedupe_key="main", push_version=False)`。
- **实测例子**：产物 `art_9128a56dd2`「**ZARA分析切入点**」，副标题「基于 竞品与价格分析 的字段资产推荐」，4 个切入点。
- **代码**：`conversation_service.py:968` · `canvas_orchestrator.py:15`（plan_explore）
- **边界**：推荐为空 → 不落卡，只回一句引导。

## F3.2 `data_query` → `_handle_data_query`

- **做什么**：取数主分支。**先做品牌消歧（关卡①），通过后才进执行层**。
- **什么时候触发**：`intent == data_query`。
- **内部怎么做**：
  1. `_ensure_dimension_options` 拿维度；
  2. 定 `keys`：优先用路由给出的 `dimension_keys`，没有就**取 options 的前 2 个**；
  3. 写 `working_memory.selected_dimension_keys = keys`；
  4. `resolve_brand(scene, term=working_memory.brand, pinned=confirmed_field_values)`；
  5. `if resolution.get("needs_confirmation")` → **停在这里**落消歧卡（**一条 SQL 都不发**）；否则 `_execute_goals`。
- **实测例子**：「先看近 5 个月的纤维混纺和价格带，出图直观点」→ 落 2 张图表卡（**37 行 / 29 行**）。
- **代码**：`conversation_service.py:987` · 判断在 `:1000` 附近
- **边界**：没有 key 且选项为空 → `goals` 为空 → 只回文案，不报错。

## F3.3 `report_build` → `_handle_report_build`

- **做什么**：按页数生成大纲，**已出图的维度自动绑到对应页**；不重复取数，只引用已有产物 id。
- **什么时候触发**：`intent == report_build`。
- **内部怎么做**：`plan_report_build(page_count, chart_cards)` → 写 `outline_card`（`dedupe_key="outline"`）；绑定逻辑是把已有的 `chart_card` 依次挂到 `page.bound_artifact_id`。
- **实测例子**：产物 `art_563ef46b49`「**ZARA汇报大纲**」，4 页、其中 **2 页自动绑定**（Page2→纤维图、Page3→价格带图）。
- **代码**：`conversation_service.py:1594` · `canvas_orchestrator.py:90`
- **边界**：一张图卡都没有 → 大纲页全部未绑定，仍可生成（后面还能补图）。

## F3.4 `canvas_revision` → `_handle_revision`

- **做什么**：改大纲 —— 按维度**删页**（连带移除对应图表）、按**页码换页**；句子里出现「生成 / ppt」时**顺手编译 PPT**。
- **什么时候触发**：`intent == canvas_revision`。
- **内部怎么做**：`plan_canvas_revision` 综合 `page_index` 与维度关键词 → 删或换 → 需要时调 `compile_deck`。
- **实测例子**：「色彩不要了」→ 移除色彩对应的图与页；**若当前大纲没有色彩页，会明确回一句「因此没有删除任何页面」**——如实说明，不假装成功。
- **代码**：`conversation_service.py:1613` · `canvas_orchestrator.py:123`
- **边界**：与 F2.2 联动 —— 「色彩不要了，直接生成PPT」实际被路由到**这里**，所以**不会**生成 PPT。

## F3.5 `rollback` → `_handle_rollback`

- **做什么**：从**最近一个带历史**的产物回退一版；确实没历史就如实说"没有可回退的版本"。
- **什么时候触发**：`intent == rollback`。
- **内部怎么做**：`rollback_latest` 倒序扫 `working_memory.produced_artifact_ids`，找到第一张 `history` 非空的卡 → `rollback_artifact`：`pop()` 出最后一个快照，恢复 `title/subtitle/payload`，并把 `version` **退回快照里的版本号**（不是 +1）。
- **实测例子**：第 7 轮说「回退一下」时，两张图卡都还是 `v=1`（重新取数发生在第 10/12 轮）→ 回复「当前没有可回退的历史版本」。**判定正确，不是 bug。**
- **代码**：`conversation_service.py:1683`（_handle_rollback）· `:331`（rollback_latest）· `:317`（rollback_artifact）· `canvas_orchestrator.py:158`
- **边界**：`history` 只保留**最近 10 版**（`existing.history[-10:]`），更早的退不回去。

# L4 执行层 · `data_query` 内部（F4.1–F4.9）

> **四个入口、一个漏斗**：首次取数 / 消歧后 / 澄清后 / 抽屉后，全都汇到 `_execute_goals`。这样重试**永远不会**和第一次跑偏。

## F4.1 品牌归一 `resolve_brand`

- **做什么**：把你口语里的品牌名，去标准字典里解析出候选，并按"分数、记录数"排序去重。它是消歧判定的**数据源**。
- **什么时候触发**：`data_query` 分支、`_execute_goals` 内部各调一次（第二次带上了已确认的值）。
- **内部怎么做**：调 `field_value_resolver_service` 在场景的品牌字段上做匹配；命中策略会带 `strategy` 标记（`normalized_exact` / `contains_candidate` / `normalized_exact_with_note` 等）；带 `pinned` 时优先复用人工确认过的值（`strategy="user_confirmed"`）。
- **实测例子**：输入「THE NORTH FACE」→ 解析出 **7 个候选**：325 / 185 / 86 / 62 / 29 / 5 / 0。这些数字是 `clothing_info` join `dict_brand_info` 按品牌变体统计的**真实记录数**。
- **代码**：`conversation_service.py:352`
- **边界**：字典里查不到 → `confirmed=[]`，走无品牌路径（不阻塞取数）。

## F4.2 关卡① 字段消歧 `_ask_field_resolution`

- **做什么**：候选**不占优势**时**只落卡、不发 SQL**，把待决状态记到工作记忆；用户选过的值写进 `confirmed_field_values`，之后**永不重复问**。
- **什么时候触发**：`resolve_brand` 返回 `needs_confirmation=True`。
- **判定公式**（`_has_dominant_candidate`）：
  ```
  候选数 ≤ 1                                  → 占优，直接取数
  top_count ≥ second_count × 3                → 占优，直接取数（ZARA 3772 vs 4）
  top_count > 0 且 second_count == 0          → 占优
  退化为分数比：top_score ≥ second_score × 1.35 → 占优
  否则                                        → needs_confirmation，落卡
  ```
  **为什么用记录数而不是候选个数**：品牌字典里的区域变体（`THE NORTH FACE` / `THE NORTH FACE（日本）` / `北面（淘宝）`）归一化后会落到同一个键，所以"候选多"是常态；"两个都像人话、量级还接近"才是真疑问。代码注释原话：*3772 vs 4 is a decision, 325 vs 185 is a question.*
- **实测例子**：产物 `art_fb2770b1f8`「品牌「THE NORTH FACE」需要确认」；候选 325 vs 185，**325 < 185×3 = 555 → 落卡，0 条 SQL**。对照组：ZARA 3772 vs 4 → 3772 ≥ 12 → 直接出图，只在回复里附一句"已按谁取数"。
- **代码**：`conversation_service.py:1271`（_ask_field_resolution）· `:462`（_has_dominant_candidate）
- **边界**：已在本次会话选过 → 命中 `confirmed_field_values`，**绝不问第二遍**。

## F4.3 目标编排 `plan_data_query`

- **做什么**：把选中的维度翻译成 `goal`（一句话意图 + 图表建议 + 指标 + 维度），并把品牌与时间窗**拼进 goal 文本**。
- **什么时候触发**：`_execute_goals` 开头。
- **实测例子**：`{ dimension_key: "price", goal: "ZARA 各二级类目的价格分布情况（近5个月）", chart_hint: "histogram" }`。
- **代码**：`canvas_orchestrator.py:42`
- **边界**：`goals` 为空 → 直接回文案。

## F4.4 并行取数 `_run_goals`

- **做什么**：用线程池并发跑多个 goal，**并发上限 3**；单维度异常被捕获成一条失败结果，**不会拖垮其它维度**。
- **什么时候触发**：`_execute_goals`。
- **内部怎么做**：`workers = min(MAX_PARALLEL_QUERIES, max(1, len(goals)))`，`ThreadPoolExecutor(thread_name_prefix="conv-query")`，`as_completed` 收集；每个 future 的异常在循环里被捕获。
- **实测例子**：一次请求里 2 个维度同时跑，两块图卡几乎同时出现（纤维 37 行 / 价格带 29 行）。
- **代码**：`conversation_service.py:668` · 上限常量 `:47`（`MAX_PARALLEL_QUERIES = 3`）
- **边界**：超过 3 个维度会排队，不是全并发。

## F4.5 单维度取数 `_run_goal`

- **做什么**：真正调 SQL Agent。把三类"人的决定"注入到查询上下文里。
- **什么时候触发**：每个 goal 一次。
- **内部怎么做**（三个注入点）：
  1. **已确认的标准值** → `context["field_resolution"]["confirmed_resolutions"] = merged`（`_merge_confirmations(brand_resolution.confirmed, confirmations)`）。这是让下游两道闸门放行的凭据。
  2. **澄清回答** → 拼进意图文本：`intent_text = f"{intent_text}。补充口径要求：{clarify}"`。
  3. **抽屉参数** → `_apply_query_params` 折进 `context["price_band_policy"]`。
  - 调用：`self.sql_agent.run(scene=..., session_id=conversation_id, scene_version=..., intent=intent_text, context=context, execute=True)`。
  - 取数：`rows = list(getattr(query_run, "result_preview", None) or [])` —— **画布数据的唯一出口**；拿不到就是空列表，**没有兜底造数分支**。
- **实测例子**：确认品牌后，下一轮请求里带上 `confirmed_resolutions:[{table_name:"dict_brand_info", field_name:"Name", canonical_value:"THE NORTH FACE"}]`。
- **代码**：`conversation_service.py:549`
- **边界**：异常 → `status="failed"`，`error=f"取数失败：{exc}"`。

## F4.6 两道 SQL 安全闸门

- **做什么**：在 SQL 真正执行前拦两道：
  - **闸门 A** `find_unresolved_filter_conditions`：查 filters 里**未解析**的字段值——歧义不放行。
  - **闸门 B** `find_controlled_sql_filter_issues`：查**已生成 SQL** 里的 `列 = '字面量'`——受控字段没落到唯一标准值不放行。
- **什么时候触发**：每次 SQL Agent 执行。
- **内部怎么做**：两道闸门都新增了**可选参数** `confirmed_values`；人工钉过的值（`canonical_value` 命中）**直接放行**。老调用方**不传该参数 → 行为一字不变**（零影响承诺）。
- **实测例子**：这正是之前 **TNF 全维度失败的根因** —— 闸门只认配置页钉的值，不认对话里选的值。修复后，对话里选的值可以通过 `confirmed_values` 穿透。
- **代码**：`field_value_resolver_service.py`（`find_unresolved_filter_conditions` / `find_controlled_sql_filter_issues` / `_confirmed_canonical_values`）· `sql_result_agent_service.py`（`_confirmed_field_resolutions` 并在 `run()` 里传入）
- **边界**：闸门只对**受控字段**生效，自由文本字段不受影响。

## F4.7 规格与结论 `chart_spec_service`

- **做什么**：把查询结果转成**渲染无关**的图表规格（列、行、图型、findings），再生成一句中文结论。规格同时供前端 ECharts 和 python-pptx 使用。
- **什么时候触发**：单维度取数成功时（`_run_goal` 内）。
- **内部怎么做**：
  - `build(rows, chart_hint, metric_hint, dimension_hint, title, max_rows=60)`
  - **展示截断**：`limited = clean_rows[:max(1, max_rows)]`，但同时写入 `total_rows = len(clean_rows)` —— **上限 60 行、且如实声明总数**（这是"如实声明"，不是造假）。
  - 图型判定 `_decide_chart_type`：占比类字段且 2–8 行 → 饼图；`pie` 但超 10 行或有多系列 → 换柱状图。
  - `narrative()`：`f"{title}。{'；'.join(findings[:2])} 该结论基于 {total_rows} 条查询结果。"`
- **实测例子**：纤维混纺 → 5 列 / **37 行** / `chart_type=area`；结论「有机棉 在纤维占比_合计上累计占比最高，约 **53.4%**」。截断例：`art_2bd9e48021` 只带前 60 行，但 `spec.total_rows = 63`、`payload.rows_count = 63` 都如实声明了。
- **代码**：`chart_spec_service.py:56`（build）· `:65`（max_rows=60）· `:135`（_decide_chart_type）· `:248`（narrative）
- **边界**：`rows` 为空 → 走 F4.8 的空结果澄清，不进这里。

## F4.8 关卡② 口径澄清 `_ask_clarification`

- **做什么**：引擎"拒答"或"空结果"时，把死路变成**一个问题**（而不是一张堆满报错的失败卡）。
- **什么时候触发**：`_classify_failure` 返回 `needs_clarification` 或 `empty_result`，两个条件满足其一：
  - **空结果**：`status == "succeeded" and not rows`（SQL 跑通了，但这个口径没数据）。
  - **引擎要求补口径**：报错文本命中 **6 个标记**之一 —— `未返回可执行 SQL` / `缺少` / `需要确认` / `无法在不确认` / `需要明确` / `请先确认`。
  （判定文本 = `error` + `notes` 拼起来后压缩空白。）
- **内部怎么做**：
  - 问题：`_clarify_questions` 按 `；`（或句号）切分，优先挑含标记的句子，最多 4 条。
  - 选项：`_clarify_options` 用正则 `按[^、，。；;)）(（\s]{1,24}` 从报错里**反挖**出来的，按 `/` 拆分，长度限 2–28，最多 6 个。
  - 空结果专用：`_clarify_option_entries` 生成「**不限时间（看全部可用数据）**」——**这个选项自带 `time_window: ""`**，会真的把时间窗放开；若原本有时间窗，再给一条「仍限定在「X」」。
  - 永远带**自由输入框**兜底（因为是启发式）。
- **实测例子**：产物 `art_23480b030c`「品牌竞争格局」`reason=empty_result` → 点「不限时间（看全部可用数据）」→ **38 行**出来（此前是硬失败）。
- **代码**：`conversation_service.py:1326`（_ask_clarification）· `:1186`（_classify_failure）· `:1204`（_clarify_options）· `:1225`（_clarify_option_entries）· `:1258`（_clarify_questions）
- **边界**：反挖不到选项时只有输入框；此时靠你自己描述口径。

## F4.9 真失败 → 失败图表卡

- **做什么**：既不是"问口径"也不是"空结果"，才落**失败卡**：卡片正面放一句话摘要，折叠区放驱动真实报错。
- **什么时候触发**：`_classify_failure` 返回 `failed`。
- **内部怎么做**：
  - 摘要用 `_summarize_error()` 把长报错压成一行。
  - **泛化文案会被换成更具体的诊断**：若 `sql_explanation` 为空或属于 `_GENERIC_EXECUTION_ERRORS = {"MySQL 查询执行失败。", "MySQL 查询执行失败"}`，就从 `notes + insight_summary` 里取第一条真实信息。
  - `error_detail` 里保留 `reason + notes + insights` 去重后的全文（折叠区展示）。
- **实测例子**：泛化文案 `MySQL 查询执行失败。` 被替换成驱动真实信息（如 `Unknown column 'bucketed.raw_width'`）。
- **代码**：`conversation_service.py:1094`（失败卡落卡）· `:605` 附近（错误提取）· `:46`（_GENERIC_EXECUTION_ERRORS）
- **边界**：这是 LLM 生成的 SQL 质量问题，与关卡机制无关，**不稳定、会随模型变**。

# L5 落卡层 · 产物生命周期（F5.1–F5.6）

> 产物不是"一段 HTML"，而是**有身份的卡**：`kind + payload + lineage + version + history`。

## F5.1 按 `dedupe_key` 覆盖写卡 `_upsert_artifact`

- **做什么**：**同一个 key 永远只对应一张卡** —— 命中就覆盖内容并按需升版本、旧版压进 `history`；没有就新建。所以画布**不会越聊越长**。
- **什么时候触发**：每次要往画布写东西。
- **内部怎么做**：
  - `existing = _find_by_key(conversation_id, kind, dedupe_key)`
  - 命中时：`push_version=True` 才把当前内容快照进 `history`（`history[-10:]` 只留 10 版）并 `version += 1`；然后覆盖 `title/subtitle/payload/status`，`lineage` 做**浅合并**；`push_version=False` 则**原地刷新不升版本**（F1.3 重建维度卡就走这条）。
  - 新建时：`artifact_id = f"art_{uuid4().hex[:10]}"`，并把 id 追加进 `working_memory.produced_artifact_ids`；`chart_card` 还会进 `chart_artifact_ids`。
  - `dedupe_key` 约定：维度卡 `"main"`、大纲 `"outline"`、图表卡 = `dimension_key`、澄清卡 = `"clarify:{dimension_key}"`。
- **实测例子**：`art_73581d7d71`（价格带）在第 2、5、6 轮反复取数后 `version=3`，而画布**始终只有 1 张**价格带卡。
- **代码**：`conversation_service.py:204`
- **边界**：`history` 上限 10 版。

## F5.2 成功取代待确认 `_remove_by_key`

- **做什么**：某维度取数成功后，**主动移除它的待澄清卡**，避免画布上留一张已经没用的问句。
- **什么时候触发**：`_execute_goals` 里该维度成功的那一支。
- **实测例子**：价格带维度成功后，按 key `clarify:price` 删掉对应澄清卡。
- **代码**：`conversation_service.py:279`（_remove_by_key）· 调用在 `:1121`
- **边界**：只删"澄清卡"，不删图卡。

## F5.3 关卡③ 参数抽屉 `_apply_requery`

- **做什么**：图表卡上点「高级参数」改完重跑：**白名单**只认价格带 4 项 + mode，畸形 payload **改不动别的东西**；复用同一 goal，**覆盖同一张卡**。
- **什么时候触发**：在图表卡的抽屉里点「重新取数」→ `POST …/artifacts/{id}/resolve`（body 带 `params`）→ `apply_artifact_action` 按 `kind == chart_card` 分派到这里。
- **内部怎么做**：
  - `_apply_query_params` 的**白名单**：`strategy` / `bucket_count` / `boundary` / `fixed_template`，外加 `mode`（`mode` 还会写 `context["price_band_mode"]`）。只把非 `None` 的键合进 `price_band_policy`。
  - `keys=[dimension_key]`，`time_window` 优先取 params 里的，其次取卡上带的时间窗。
  - 映射到 SQL Agent **本来就读得懂的** `context.price_band_policy`，**没有引入新词汇**。
- **实测例子**：ZARA 价格带 → 改「分位数 + 6 个桶」→ 覆盖同一张卡，`version 2→3`；回复里带一句「价格带 分位数、6 个桶、时间窗口 不限」。
- **代码**：`conversation_service.py:1540`（_apply_requery）· `:648`（_apply_query_params）
- **边界**：卡上没有 `dimension_key` → 直接返回错误「该卡片没有可重新取数的维度」。

## F5.4 确认 / 澄清回写 `apply_artifact_action`

- **做什么**：画布上**所有人工动作走同一个入口**，按卡型分派：
  | 卡型 | 分派到 | 效果 |
  |---|---|---|
  | `resolution_card` | `_apply_resolution` | 写 `confirmed_field_values` → 重新取数 |
  | `clarification_card` | `_apply_clarification` | 写 `clarifications` → 重新取数（选项可携带新时间窗） |
  | `chart_card` | `_apply_requery` | 改参数 → 重新取数 |
- **什么时候触发**：`POST /api/v1/conversations/{id}/artifacts/{aid}/resolve`，body 是 `{value}` / `{answer}` / `{params}`。
- **内部怎么做**：
  - 前置校验：卡必须属于该会话；**选的值必须在卡的候选里**（否则返回「所选值不在本题候选中」）。
  - `_apply_resolution`：按 `(table_name, field_name, term)` 三元组**去重后追加** `confirmed_field_values`（`strategy="user_confirmed"`）；卡标 `ready` + `payload.chosen`；`pending_blocker=None`；然后 `_execute_goals`。
  - `_apply_clarification`：若命中的选项带 `time_window` 就**覆盖时间窗**；把口径写进 `wm.clarifications[dimension_key]`，**但 `reason == "empty_result"` 时不写**（避免"不限时间"被当成永久口径固化）；然后 `_execute_goals`。
- **实测例子**：选「不限时间」**不是只改文案**——该选项自带 `time_window:""`，会真的把时间窗放开后重跑，得到 **38 行**。
- **代码**：`conversation_service.py:1377`（apply_artifact_action）· `:1410`（_apply_resolution）· `:1486`（_apply_clarification）
- **边界**：**没有幂等保护** —— 每次调用都会**无条件重跑取数并追加一条助手消息**。这是**缺陷 A** 的根因（见文末）。

## F5.5 改内容 `revise` / 回退 `rollback`

- **做什么**：`revise` 改卡内内容（标题、图型、换绑页）；`rollback` 从 `history` 恢复上一版；`rollback_latest` 回退全局最近那张。
- **什么时候触发**：`POST …/artifacts/{aid}/revise`、`POST …/artifacts/{aid}/rollback`；大纲页另有 `PATCH …/outline/pages/{pid}`。
- **内部怎么做**：
  - `revise_artifact`：**先压快照再改**（`history.append(current)` → `history[-10:]` → `version += 1`），支持 `title/subtitle/payload`（浅合并）+ `chart_type`（改图型时把 `status` 置回 `ready`）。
  - `rollback_artifact`：`pop()` 最后一个快照 → 恢复 title/subtitle/payload → **`version` 退回快照里的版本号**。
- **实测例子**：PPT 页卡片上「换成柱线图」走 `revise`，**只改这一页的 chart_type，不重新取数**。
- **代码**：`conversation_service.py:285`（revise）· `:317`（rollback_artifact）· `:331`（rollback_latest）
- **边界**：`revise` 是**浅合并** payload，不会整份替换。

## F5.6 PPT 装配与导出 `compile_deck`

- **做什么**：大纲 → 逐页装配图表数据与单页文案 → 生成可预览、可导出的 deck 卡（16:9）。
- **什么时候触发**：`POST /api/v1/conversations/{id}/outline/compile`；或 F3.4 里句中出现「生成/ppt」时顺手调。
- **内部怎么做**：`compile_deck` 读大纲页 → 逐页取绑定的 `chart_card` 的 `spec.rows` → 组装 `SlideDraftDTO` → `save_deck_card` 写 `deck_card`；`export_deck` 交给 python-pptx 生成文件，`GET …/decks/{did}/export.pptx` 下载。
- **实测例子**：产物 `art_ba97ca33d6`，`deck_id=deck_458e303366`，4 页，导出 **48105 字节 / 4 页** PPTX；老链路回归也是同一结果。
- **代码**：`conversation_service.py:853`（compile_deck）· `:824`（save_deck_card）· `:871`（export_deck）
- **边界**：页未绑图 → 该页只有文案，不报错。

# L6 呈现层 · 前端按 `kind` 分派渲染（F6.1–F6.4）

> 新增一种卡型只需要加一个 `renderer`，**不动对话主循环**。

## F6.1 画布重绘 `renderCanvas`

- **做什么**：清空重画，但**先记住 `scrollTop` 再写回**；每张卡带 `data-artifact-id` / `data-kind`，便于定位与测试。
- **什么时候触发**：`state.canvas` 变化后（`renderCanvas()` 被调用时）。
- **内部怎么做**：`keepScroll = box.scrollTop` → `disposeCharts()`（销毁旧 ECharts 实例，防内存泄漏）→ `innerHTML = ""` → 逐张 append（带 `animationDelay`）→ `box.scrollTop = keepScroll` → `revealPendingCheckpoint(items)`。
- **实测例子**：切换图表页签后**不再跳回画布顶部**（这是之前实测出来的真 bug，已修）。
- **代码**：`agent.js:344` · `cardShell :401`
- **边界**：画布为空时显示引导文案，并清空「共 N 个产物」的计数。

## F6.2 六个 renderer

- **做什么**：按 `kind` 分派渲染 6 种卡。
  | kind | 长什么样 |
  |---|---|
  | `dimension_card` | 多选维度（点选后走「看选中的维度」） |
  | `chart_card` | 图 + 表 + SQL 折叠区 + 「高级参数」抽屉 |
  | `resolution_card` | 候选列表，每项带记录数，点选即确认 |
  | `clarification_card` | 问题 + 选项 chip + 自由输入框 + 提交 |
  | `outline_card` | 可改页、可换绑图 |
  | `deck_card` | 翻页预览 + 导出 |
- **什么时候触发**：`renderCanvas` 对每张卡查 `renderers[card.kind]`。
- **实测例子**：上一轮只加了 `resolution_card` / `clarification_card` 两个 renderer，**对话主循环一行没改**。
- **代码**：`agent.js:426`（renderers 对象）· 各 renderer：`:427 / :479 / :628 / :665 / :725 / :784`
- **边界**：遇到未知 `kind` → `defaultCard` 兜底（不会白屏）。

## F6.3 自动滚到待操作卡 `revealPendingCheckpoint`

- **做什么**：画布产物变化时，如果存在**待确认 / 待澄清**的卡，**自动滚进视野**，避免它在折页下方点不到。
- **什么时候触发**：`renderCanvas` 末尾；靠一个签名（`artifact_id:status` 拼接）判断"画布集合变了"才执行。
- **内部怎么做**：倒序找最后一张 `status === "needs_confirmation"` 或 `"needs_clarification"` 的卡 → `requestAnimationFrame` 里按 `data-artifact-id` 找到节点 → `scrollIntoView({block:"nearest", behavior:"smooth"})`；有 `typeof scrollIntoView === "function"` 守卫，避免无布局的 jsdom 测试炸。
- **实测例子**：这正是"底部文字和选择被遮住"的修复点之一。**真根因**是 `.canvas` 是 flex 纵向容器，而卡片自己设了 `overflow:hidden` —— 按 flexbox 规范这会让它的自动最小尺寸降为 0，于是卡片**被压缩**而不是溢出滚动（实测 6 张卡被压成 117/164/51/148/104/72 px）。修复是 `.canvas > * { flex: 0 0 auto; }`。
- **代码**：`agent.js:374` · `agent.css`（`.canvas > *`）
- **边界**：只对"待操作"状态的卡生效，普通图卡不抢你的滚动位置。

## F6.4 图表交互

- **做什么**：ECharts 由 `spec.rows` 逐点换算，支持图/表切换、图型切换。
- **什么时候触发**：卡片渲染时（`mountChart`）以及你点页签/图型按钮时。
- **内部怎么做**：`buildOption(spec)` 构造 option，`series` 由 `rows.map(...)` 逐点算出；**无命中值是 `null` 而不是 `0`**，不会把"没数据"画成 0；`dataTable(spec)` 渲染明细表。图/表切换与图型切换**只改本地渲染，不发请求**。
- **实测例子**：面积图/柱状图切换只改本地渲染；`series` 里出现 `null` 表示该点无数据。
- **代码**：`agent.js:108`（buildOption）· `:247`（mountChart）· `:958`（dataTable）
- **边界**：`spec.rows` 只带前 60 行（F4.7 的展示截断），但表头会如实声明 `total_rows`。

# 附：两个真实缺陷（**均未修**，待决定）

**缺陷 A · 确认动作不幂等**
- 现象：`conv_7a4cccfb49` 里同一条「已确认品牌 THE NORTH FACE →（日本）」的回复**重复 17 次**（28 条消息只有 7 条不同），澄清卡 `version` 涨到 **18**。
- 根因：`apply_artifact_action` → `_apply_resolution` / `_apply_clarification` **每次调用都无条件重跑取数并追加一条助手消息**，后端没有幂等保护。
- 前端侧：`setBusy(true)` 只禁用了**发送按钮**（`$("sendBtn").disabled`），**卡里的候选按钮 / 选项 chip 没有忙保护** —— 连点两下就会发两个 POST。
- 定性：大概率由早前交互测试的重复点击造成，但真实用户双击同样复现。

**缺陷 B · 跨轮槽位拼接重复**
- 现象：一张失败卡的 `goal` 是 `THE NORTH FACE ZARA 各二级类目的价格分布情况` —— **两个品牌焊在一起**，下游直接拒绝。
- 根因：品牌记忆（F2.5）是**覆盖**语义，但 goal 文本（F4.3）是**拼接**语义。当轮槽位应**覆盖**同名上下文槽位，而不是追加。

**另外三条已知边界**
- 意图路由全靠中文关键词，同义词/英文/口语会漏判 → 退化到 explore 兜底（不出错，但要多说一轮）。
- 前后端时间窗词表必须同步：前端 4 项、后端 6 条正则，任一边改了另一边没改，时间窗就会错位。
- 消歧阈值 ×3 是经验值：对字典里记录数分布极不均衡的品牌敏感，改它要重跑回归。
