### 本轮新增的两件事

**① `merge_pages`：把"第 2 页和第 3 页合并，突出混纺趋势"真的做出来**

- 契约：`page_ops` 新增
  `{"op": "merge_pages", "page_indexes": [2, 3], "emphasis": "混纺趋势"}`；
  明确写了"点名合并**不许**改用 `balance`"（`balance` 从尾部压缩，会合错页）。
- 归一化：`canvas_action_service.normalize_page_ops` 校验页码存在、至少两页；
  `emphasis` 原话带下去。
- 合并规则（`report_composer.merge_pages`）：
  - 保留页**优先取有真实图表的那一页**；保留页没图、被合并页有图 → **把图接过来**；
  - 被合并页的标题/目标/要点/结论折进保留页（`findings` + `narrative`），内容不丢；
  - `emphasis` 落到目标的 `objective` 和 `narrative` 上，不是只回一句"已突出"。
- 与"整页替换"的冲突：agent 给合并命令时会同时带 `target.page_index`，
  旧逻辑会在合并后拿原话把这一页**再替换一次**（合并结果被抹掉、文案还说"已替换为"）。
  已加 `structural_orders` 闸门：删除/合并过的页码不再参与整页替换，措辞也不再自称"替换"。

**② 大纲回退按钮**

后端本来就有 `push_version` + `rollback`，但大纲卡上**没有入口**（只有图表卡有）。
现在大纲卡头部有「回退」，`history` 为空时禁用；回退后如果画布上已有 PPT 预览，自动重新装配。

**③ 顺手修掉的一个"说谎"文案**

用户说"串成一份 4 页汇报"，但会话里只有 1 张图、又没有待取数维度时，`build_outline`
只能搭 2 页，回复却照抄 requested 说"搭了一个 4 页的 PPT 骨架"。
现在按**实际页数**说，并补一句"你要的是 4 页，但当前会话能引用的图表还不够…"。

## 2. 结构性差异（**最关键的一条**，先看这个）

四模块里"模块二~四"的迭代设计，默认了一个前提：**页面是一个"重实体"**——
它自己带着 SQL、洞察、筛选条件、图表绑定、版式。老页面 `main.js` 正是这么建的。

新画布的页面是**轻投影**。`report_composer.build_outline`（`packages/.../report_composer.py:112-117`）
产出的 page 只有 6 个字段：

```python
{
  "page_id": "rpage_xxxxxxxxxx",
  "order": 2,
  "kind": "chart" | "text",
  "title": "...",
  "objective": "...",
  "bound_artifact_id": "<chart_card 的 artifact_id 或 None>",
}
```

**没有** `sql` / `chart_binding`；`findings` / `narrative` / `layout` 是后来补上的
（用户直改后成为**权威内容**，见 `set_page_content` / `build_deck`），
SQL 仍然挂在**图表卡**上，页面不持有。

> 2026-10-11 补注：下面这段描述的是 09-20 时的页面模型。`findings` / `narrative` /
> `layout` 已补进 page；`sql` 仍然只在 chart_card 上（改页面 SQL 等于改它绑的那张卡），
> 这个取舍是有意的——一张卡可能被多页引用，SQL 不能各页一份。

那幻灯片的内容从哪来？`build_deck`（同文件 `:183-225`）**直接从绑定的图表卡投影**：

```python
bound = charts_by_id.get(page["bound_artifact_id"])
if bound and bound.get("spec"):
    spec["title"] = page["title"]
    findings  = bound.get("findings") or []      # 来自 chart_card，不是来自 page
    narrative = bound.get("narrative") or ""      # 同上
else:
    narrative = page.get("objective") or ""       # 文案页只落一句 objective
```

**推论（这条决定工作量）**：模块三"拖排序/新增页"、模块四"单页重生成/预览区改字/换版式"
这些不是补几个按钮的事——**得先给新画布的页面补字段，再补对应的后端动作**。
而"改 SQL / 直改洞察"更是**直接改了上游图表卡**才会生效（因为页面本身不持有这些）。

另外一个连带结论：新画布走的是**内存产物模型**（`conversation_service` 的 `outline_card.payload["pages"]`），
**不是**老的 DB `report_plan`。`session_id=conversation_id` 只是当**参数**传给 `report_composer` 的函数，
没有落到 `report_workflow` 的持久化层。

## 3. 实测证据

### 3.1 自然语言收窄筛选不落地

探针 `/tmp/probe_nl_params.py`，会话 `conv_11082e3afc`：

| 轮 | 输入 | 结果 | SQL 是否含筛选 |
|---|---|---|---|
| 1 | 初次取数 | rows=27 | — |
| 2 | 「只看 400 元以上的价格带」 | rows=56 | **`"400": False`**、`price_band: null`、`clarify: ""` |
| 3 | 「时间从 5 个月改成 3 个月」 | rows=39 | ✅ `INTERVAL 3 MONTH` 真落地 |

结论：**时间窗类改动能落地，值筛选类不能**。第 2 轮行数反而变多（27→56），说明是重跑了默认口径，
而不是套上了 400 元的下限。`clarify` 也是空的——系统既没做，也没问。

### 3.2 自然语言换图表形态被误判

同一会话，输入「换成折线图」：

```
intent = canvas_revision      ← 判错了
回复 = "画布上目前还没有汇报大纲……"
```

用户想改的是**图表卡形态**，系统理解成**改大纲**，且因为没有大纲就回了一句答非所问的话。
（好消息：这轮没出卡、没造大纲，说明 2026-09-16 的"没有大纲不许自己造"守卫是生效的。）

### 3.3 缺失项的静态确认

在 `apps/vibe_frontend/static/agent.js` 中检索：`draggable` / `dragstart` / `换一批` / `待补数` /
`regenerate` / `重新生成` / `textarea` —— **全部 0 命中**。
（`待取数` 有 1 处，是 `outline_card` 里的只读徽标 `chip("待取数","warn")`，不是调度动作。）

### 3.4 能力边界

可用维度**只有 4 个**：`fiber` / `price` / `brand` / `color`。
没有"尺码""地域"等。所以"换一批维度"能换的东西其实有限——这条要么扩展维度资产，要么就不做。

## 4. 可直接迁移的资产（符合"老功能逐步迁移"的既定要求）

老页面 `apps/vibe_frontend/static/main.js` 里**已经有完整实现**，不必重写：

| 老页面实现 | 位置 | 对应端点 |
|---|---|---|
| SQL `<textarea>` + 「保存 SQL 修改」+「确认执行 SQL」 | `main.js:5031` / `:5106` / `:5109` | `PUT …/pages/{id}/sql`、`POST …/pages/{id}/execute` |
| 洞察 `<textarea>` + 「生成结论」「保存结论」「确认本页并写入 PPT」 | `main.js:5024` / `:5116` / `:5119` / `:5124` | `POST …/generate-insight`、`PUT …/insight`、`POST …/approve` |
| 删除本页 / 保存本页大纲 | `main.js:5022` / `:5094` | `DELETE …/pages/{id}` |
| 页面类型/图表类型/分类字段/数值字段/展示条数/数据筛选 表单 | `main.js` 报告工作流段 | `PATCH …/pages/{id}`、`POST …/confirm-chart` |
| 生成 SQL | `main.js:5097` | `POST …/pages/{id}/generate-sql` |

后端 `apps/vibe_backend/app/routers/report_workflow.py` 也有**全套**端点（18 个，含
`pages` 的 POST/PATCH/DELETE、`generate-sql`、`sql`、`execute`、`confirm-chart`、
`generate-insight`、`insight`、`approve`、`export.pptx`）。

**但注意 §2 的坑**：这些端点操作的是 **DB report_plan**，而新画布的页面是**内存模型**。
所以迁移有两条路：

- **路线 A（推荐，改动小）**：新画布**只迁交互**，不迁持久化——即给 `outline_card.payload.pages`
  补上 `sql` / `findings` / `narrative` 字段，在 `conversation.py` 下加对应的
  `PATCH/PUT/POST …/outline/pages/{page_id}/…` 端点，内部仍写内存产物。
  老端点、老页面**一行不动**（零影响原则）。
- **路线 B（改动大）**：让新画布真的建 `report_plan`，复用老端点。
  风险：新画布的产物卡模型（version/history/dedupe_key/lineage）与 report_plan 的版本模型要打通，
  不建议现在做。

## 5. 建议补齐优先级

### P0 — 修"已经承诺但没生效"的（用户会立刻撞到）

1. **自然语言收窄筛选落地**（§3.1）。`_apply_requery` 要把值筛选（`>=400` 这类）解析成
   `price_band.min` 之类的真实参数并进 SQL；解析不出来就**追问**，不能静默忽略。
   —— 这条直接违反"不确定就继续问"的既有约定，属于 bug 而非缺功能。
2. **自然语言换图表形态**（§3.2）。"换成折线/柱状/饼图"应路由到 `chart_card` 的 revise，
   而不是 `canvas_revision`。需要补 SOUL.md 的判定规则 + 给 agent 的输入里带上图表卡类型。

### P1 — 迁移老页面现成能力（性价比最高，符合既定路线）

3. **图表卡：SQL 只读 → 可编辑 + 重新运行**（迁 `main.js:5031/5106/5109`）。
   这是"数据探索"模块最核心的可信度入口——用户能自己看、自己改、自己跑。
4. **大纲页：洞察直改 + 单页确认**（迁 `main.js:5024/5116/5119/5124`）。
5. **大纲页：拖拽排序 + 新增空白页**（老页面有"新增页"端点 `POST …/pages`）。

### P2 — 增强（体验型，可后置）

6. 「换一批维度」（§3.4：先确认要不要扩维度资产）。
7. 指令式压缩合并（"压到 3 页"）——把机械裁剪换成按主题合并。
8. 单页局部重新生成、预览区直改字、单页换版式。
9. 批量补数调度（"把待取数的页都跑一遍"）。

### 不建议做

- 方案4（场景锁定）——用户已明确搁置，见 `docs/遗留方案备选清单_2026-09-14.md`。
- 改老页面。老功能经用户确认"没有任何问题"。
