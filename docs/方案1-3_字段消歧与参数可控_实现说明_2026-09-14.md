## 1. 三个方案不冲突（先回答这个问题）

它们处在**取数流程的不同阶段**，机制可复用、语义不重叠：

```
用户一句话
   │
   ├─ 【方案1 消歧确认卡】  值不明确 → 拦在取数之前，要一个"选哪个标准值"
   │        ↓ 选定后
   ├─ 【方案2 澄清卡】      引擎拒绝猜口径 / 时间窗内空 → 要一个"按什么口径/怎么处理"
   │        ↓ 回答后
   └─ 【方案3 参数抽屉】    图已出 → 改参数原地重取（分桶策略/桶数/时间窗口）
```

方案 1、2 共用同一套「阻塞卡」机制（同一张卡 → 同一个确认动作 → 同一个续跑入口）；方案 3 是取数**之后**的调参入口。
唯一耦合点是**确认结果都要透传到 SQL 生成**，这一点三者共用同一条通道（见 §5）。

## 2. 根因复盘：为什么 ZARA 能过、The North Face 必挂

这是上一轮最反直觉的一点，值得单独记下来。

`field_value_resolver_service._resolved_payload()` 里有一行：

```python
ambiguous = strategy in {"normalized_exact", "contains_candidate"} and len(unique_candidates) > 1
```

而 `normalize_lookup_value()` 会**丢掉括号注释**，于是品牌字典里这些条目全部归一成同一个键：

| 原值 | 归一化后 | 记录数 |
|---|---|---|
| `THE NORTH FACE` | `thenorthface` | 325 |
| `THE NORTH FACE（日本）` | `thenorthface` | 185 |
| `北面（淘宝）` | `thenorthface` | 86 |
| `The North Face（美国）` | `thenorthface` | 62 |
| …（共 7 个） | | |

→ 命中数 = 7 > 1 → **判为 ambiguous** → 两道安全闸（未命中闸 + 受控字段闸）同时拦截 → 该品牌**所有**取数请求全挂。

ZARA 之所以没事，纯属**标准值里带了括号**：`ZARA（中国）` 走的是 `normalized_exact_with_note` 分支，而那个分支**不在**判定 `ambiguous` 的集合里，于是只有 1 个真实精确命中，顺利放行。

**所以不是"The North Face 有问题"，是"标准值不带括号就必挂"** —— 一个隐藏很深的地雷。

而会话层当时做的事是：`resolve_brand()` 自动取 top1 并"告知用户"，然后把这个自动选择塞进提示词——**但下游两道闸根本不认这个自动选择**。结果是「看起来处理了，实际必失败」，报错信息还极具误导性（提示里的"候选"其实是字典全量前 8 条，与用户输入无关）。

## 3. 方案 1 — 消歧确认卡 `resolution_card`

### 3.1 判定规则：不是"候选 >1 就问"，而是"没有明显主导项才问"

一开始想做成"只要候选 >1 就弹卡"。实测立刻发现问题：**ZARA 也会弹**（2 个候选），把"说一句话就出图"的顺畅体验打断。

改成用**记录数**判断（这正是人会用的直觉）：

```python
def _has_dominant_candidate(ordered) -> bool:
    top, second = ordered[0], ordered[1]
    if top_count and second_count:  return top_count >= second_count * 3   # 3772 vs 4  → 不问
    if top_count and not second_count: return True
    ... # 退化到 score 比较（1.35 倍）
```

| 输入 | 候选情况 | 处置 |
|---|---|---|
| `ZARA` | 3772 vs 4（943 倍） | **不问**，直接用 `ZARA（中国）`，一句话告知 |
| `The North Face` | 325 vs 185（1.76 倍） | **问**，7 个候选全部列出（含各自记录数） |
| `北面` | 仅 1 个候选 | 不问 |

### 3.2 卡片与续跑

卡片列出**每个候选的真实记录数**（这是用户做判断的唯一依据），点选后：

1. 把选择写入 `working_memory.confirmed_field_values`（**term + table.field + canonical 三元定位**，可反复覆盖同一词）
2. 卡片状态转为 `已确认标准值：X`（保留在画布上，是决策留痕）
3. **立刻续跑**：用卡上缓存的 `dimension_keys` + `time_window` 重新取数

### 3.3 关键修复：让两道安全闸认"人工已确认"

`field_value_resolver_service` 的两道闸各加一个**可选**参数 `confirmed_values`：

```python
def find_unresolved_filter_conditions(..., confirmed_values=None)
def find_controlled_sql_filter_issues(..., confirmed_values=None)
```

命中即放行。**老调用不传这个参数 → 行为逐字节不变**，这是"不影响原功能"的技术保证。

值从既有 context 推导，SQL Agent 无需改签名：

```python
confirmed_field_values = self._confirmed_field_resolutions(context)   # 读 field_resolution.confirmed_resolutions
```

## 4. 方案 2 — 澄清卡 `clarification_card`

### 4.1 两个触发源

| reason | 触发条件 | 卡片给的选项 |
|---|---|---|
| `needs_clarification` | 引擎明确拒绝猜（"缺少构成口径定义…需要确认是按SKU加权/按成分行求和/还是按SKU数占比"） | 从报错里挖出的口径选项 + 自由输入 |
| `empty_result` | **SQL 执行成功但 0 行**（如 TNF 数据是去年的，"最近30天"天然为空） | 「不限时间（看全部可用数据）」等一键处理 |

分类器：

```python
def _classify_failure(outcome) -> str:
    if outcome.get("empty_result"):        return "empty_result"
    if any(marker in text for marker in CLARIFY_MARKERS): return "needs_clarification"
    return "failed"     # 真硬失败 → 仍是失败图表卡
```

### 4.2 顺带修掉一处误导读数

修前 `empty_result` 把 **intent 原文当成错误信息**贴在卡上（用户完全看不懂）。现在输出：

> 查询执行成功，但该口径下没有数据——这个品牌/类目在所选时间窗口内可能没有记录，可以换一个时间窗口，或去掉时间限制后重试。

并且直接变成**可点的澄清卡**，一键放开时间窗。

### 4.3 选项挖掘（启发式，自由输入兜底）

从报错文本里抓 `按…` 片段，对真实报错的挖掘结果：

```
['按SKU加权', '按成分行直接求和', '按SKU数占比', '按天', '按周', '按月']
```

选项用**字典**承载（`{label, answer, time_window?}`），因为"不限时间"这种选择不只是措辞，还要真的改查询窗口。

### 4.4 口径记忆

用户确认的口径写入 `working_memory.clarifications[dimension_key]`，**之后每次重取都自动带上**，不必反复交代。

## 5. 方案 3 — 图表卡「高级参数」抽屉

### 5.1 暴露的旋钮

| 控件 | 取值 | 落点 |
|---|---|---|
| 价格带分桶策略 | 自适应（等宽+整百/整千取整） / 分位数 / 等宽 | `context.price_band_policy.strategy` |
| 分桶数 | 2–20 | `context.price_band_policy.bucket_count` |
| 时间窗口 | 最近30天 / 近 6 个月 / 近 12 个月 / 不限 | 重建 goal 文本 |

**没有新增任何后端词汇** —— 全部复用 SQL Agent 早已支持的 `context.price_band_policy` / `price_band_mode`。

### 5.2 白名单（防止参数越权穿透）

```python
def _apply_query_params(*, context, params):
    price_band = params.get("price_band")
    for key in ("strategy", "bucket_count", "boundary", "fixed_template"): ...   # 只认这几个
```

实测传入 `{"hack":"x", "dimension_key":"evil"}` 被打掉，context 只多出 `price_band_policy`。

### 5.3 参数会落盘到卡片

图卡 payload 记下 `time_window` 与 `price_band`，抽屉再次打开时回显上次设置。

## 6. 数据模型与接口变化

### 契约（`packages/shared_contracts/python_models.py`）

```python
ArtifactKind += "resolution_card", "clarification_card"

WorkingMemoryDTO +=
    confirmed_field_values: list[dict]   # 人已确认的标准值（原"字段消歧确认"）
    clarifications: dict[str, str]       # 每个维度已确认的统计口径
    pending_blocker: dict | None         # 画布当前在等用户回答什么
```

### 新接口（1 条）

```
POST /api/v1/conversations/{cid}/artifacts/{aid}/resolve
body: { value?, answer?, params? }
```

一个入口按卡片类型分派：消歧选值 / 口径回答 / 参数重取。校验失败返 400（带可读 detail）。

### 8.2 前端

### 8.3 交互链路（jsdom 真点击 + 后端状态断言）

两段真实点击链路，零 JS 运行时错误：

```
A. 消歧卡 → 澄清卡（The North Face）
   ① 点击消歧候选「THE NORTH FACE」            → 后端记录确认值  ✓ 18s
   ② 点击澄清口径「不限时间（看全部可用数据）」  → price 维度重取后 ready  ✓ 18s
      最终画布：价格带与折扣节奏 | column | rows=38 | time_window=""
               品牌竞争格局     | 澄清卡（待用户回答）
   注：修前该链路 4 个维度全挂；现在放开时间窗后能真正取到 38 行数据。

B. 参数抽屉（ZARA 价格图）
   ③ 展开价格图卡「高级参数」（select=2 number=1）
      设 strategy=quantile、bucket_count=6 → 点「重新取数」
      → rows 26 → 60，price_band={"strategy":"quantile","bucket_count":6,"mode":"adaptive"}  ✓ 16s
```

> 过程中修掉一个**测试脚本自身**的 bug：最初用"画布上第一个『高级参数』按钮"定位，结果点到了 `brand` 维度的图卡（该卡 `isPrice=false`，于是正确地上报"价格带参数未变"）——产品行为正确，是断言打错了目标。
> 为此给卡片加了 `data-artifact-id` / `data-kind` 属性，让测试按**产物身份**而不是 DOM 顺序定位。这既是可观测性改进，也避免了同类假阳性。

### 8.4 顺手修掉一处"报错看不懂"

排查中发现价格维度出现真·SQL 执行失败，但卡面只有一句 **「MySQL 查询执行失败。」**。

实测该 SQL，真实报错是：`(1054, "Unknown column 'bucketed.raw_width' in 'field list'")`
——**LLM 生成的 SQL 引用了自己没在 CTE 里定义的列**。

问题在于真实异常被 executor 放在 `query_run.insight_summary`，而会话层只读了 `sql_explanation`。
现已改为：卡面显示摘要，展开后显示**驱动层的真实异常**。

> 这是引擎侧（LLM SQL 质量）的既有问题，与方案 1–3 无关，且不稳定复现（同一问法有时出干净 SQL、有时报错）。
> 现在至少用户能看到真实原因，且失败卡也提供了「高级参数 → 换个分桶策略重取」这条恢复路径。

## 9. 已知边界（未做，供后续）

1. **`resolution_card` 只处理品牌字段**。纤维/类目等其他受控字段若出现歧义，仍走硬失败路径。机制已通用，扩字段成本很低。
2. **消歧判定依赖记录数**。记录数为 0 或全为 0 的字典字段，会退化为"问用户"（宁可多问，不可猜错）。
3. **澄清卡只承接"引擎拒绝"**，不主动追问模糊需求（那是"维度推荐"的职责）。
4. **抽屉暂只暴露价格带策略 + 时间窗口**。老页面的「字段消歧逐个确认」「纠错词库」未纳入——前者已由方案 1 覆盖，后者未做。
5. **卡片位置**：新卡片按创建顺序追加到画布末尾；产物多时需要滚动。缺"置顶/收起"（另一条遗留项）。
6. **方案 4（场景锁定）按要求未做**，仍在遗留清单。

## 10. 一句话总结本次的设计取向

> **低门槛不等于去掉确认点。**
> 把"人工确认"从表单搬到对话里是进步；把它**删掉**是倒退——因为下游的安全闸本来就在等这个确认。
> 正确的做法是：**该问的时候问得极轻（一张卡、点一下），不该问的时候一个字都不多问（有主导项就自己决定）。**
