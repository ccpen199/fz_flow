# 时间口径必须看得见（2026-10-19）

> 用户报障（截图）：问「优衣库品牌最近一个月上了多少件T恤」，图上只有 2025-07-01 一个点，
> 条件栏只有「品牌 =优衣库（淘宝）」「二级类目 =T恤」——**完全没有时间**。
> 原话：「不然我怎么知道这些数据是哪个月份的？」

## 1. 三个真实问题（都不是"数据错了"）

| # | 现象 | 根因 |
| --- | --- | --- |
| 1 | 条件栏没有时间 | 时间窗只作为 `time_window` 传给规划器、藏在 SQL 的 `DATE_SUB(..., INTERVAL 30 DAY)` 里，**从没进过 `applied_filters`** |
| 2 | 回复里只有"（近1个月）" | 同上，没人把"这一个月到底是哪个月"写出来 |
| 3 | 图看起来是空的 | 折线系列写死 `showSymbol: false`；类目只有 1 个时，**整条线画不出来**，图表区一片空白 |

数据本身是对的：优衣库（淘宝）+ T恤 在库里是按月快照（2025-07-01、2025-02-01、2024-12-01…），
「近1个月」锚在该品牌这个类目的最新一条（2025-07-01），窗口内只有这一天有数据 →
`rows_count=1` 是真实结果，不是取数失败。

## 2. 改动

### 2.1 时间进条件栏（`conversation_service`）

- `_spec_date_range(spec)`：从**结果行**里认出日期列，返回 `(最早, 最晚, 有数据天数)`。
  只认 `YYYY-MM-DD` 前缀，不猜、不从时间窗文案倒推日期。
- `_time_filter_entry(time_window, date_range)`：
  - 只有一天 → `时间 =近1个月（数据仅 2025-07-01 一天）`
  - 有区间 → `时间 =近3个月（数据 2024-05-01 ~ 2024-07-31（12 天有数据））`
  - 没结果行 → `时间 =近1个月`（不编造区间）
- `_with_time_filter(...)`：追加为条件栏最后一行；已有"时间"条件时不重复加。
- 图表卡 payload 的 `applied_filters` 现在含这条（失败卡也带，但不带区间）。

### 2.2 结论与回复说清月份

- 卡片"数据洞察"前缀：`统计窗口：近1个月（数据仅 2025-07-01 一天）。`
- 聊天回复追加一行：`时间口径：近1个月（数据仅 2025-07-01 一天）。`

### 2.3 单点折线画得出来（前端）

`agent.js` 里折线/面积系列原为 `showSymbol: false`。改为
`var sparse = categories.length <= 2;` → `showSymbol: sparse`：
类目 ≤ 2 时必须画点，否则单点折线等于看不见。三处系列构造（多系列、归并系列、单系列）同步改。
`agent.html` 的 `?v=` 升到 `20261019-time-window-v1`。

## 4. 不做的事 / 已知边界

- **不从时间窗文案倒推日期**：区间只取结果行里真实出现的日期；没有结果就只写窗口名。
- ~~不改"近一个月"的锚点语义：仍锚在该筛选口径下的最新一条数据~~ → **当日已改，见第 5 节**。
  用户明确拍板：「最新一个月就是**库里**的最新一个月」，不接受"按品牌自身最新日期回推"。
- 天数取的是「有数据的天数」，不是窗口自然天数：数据是月快照时两者差别很大，
  写"有数据的天数"更不容易误导。

## 5. 补充：锚点改全库 + 时间窗强制落进 SQL（同日，用户拍板后）

用户连续两轮追问：「我问最新一个月，哪怕模型按自己最新日期回推没得到数据，为何还有这些数据？
这个截图的数据是全日期数据还是哪个月份的数据？」——答案：截图上那是**品牌自身最新日期**
的回推窗口（优衣库按月快照的 2025-07 前后），不是最近一个月。

### 5.1 三个叠加的根因

| # | 根因 | 证据 |
| --- | --- | --- |
| 1 | **参数没转发**：`_run_goals` 收了 `time_window`/`time_range`，`executor.submit(...)` 里却没传给 `_run_goal` | 上一版注入的绝对区间**从未执行过** |
| 2 | **system prompt 明确要求自锚**：`sql_result_client` 里写着"近/最近一律以表内最大可用日期为锚点" | 模型照做 → 在筛选后的子集上 `MAX(DATE(ci.CreateTime))` |
| 3 | **没有验收**：SQL 跑通即算成功，没人检查它用的是哪段时间 | 卡片写"最近一个月"，SQL 查的是 2025-07 |

### 5.2 改动

- **全库锚点**：`_data_time_anchor(scene)` 直接 `SELECT MAX(DATE(时间列))` over 事实表
  （实测 `2026-06-25`，与品牌无关），5 分钟缓存；`_time_bounds()` 把「近N个月/周/天」
  换算成绝对区间（终点=全库最新日期）。
- **结构化事实下推**：`_time_scope_payload()` 生成
  `{start, end, field, column, anchor, anchor_scope:"database"}` → `context["time_scope"]`
  → `sql_result_agent_service` 抬到 `llm_payload.time_scope`（顶层，模型更容易当硬约束读）。
- **system prompt 让位**：`INPUT.time_scope` 存在时视为权威，
  禁止 `MAX(日期)` 自行回推、禁止 `DATE_SUB(MAX(...))`；原来那条"以表内最大可用日期为锚点"
  降级为"仅当 `time_scope` 不存在时"。
- **失败关闭校验**：`_time_scope_violation()` + `_validate_llm_sql_output(time_scope=...)`。
  两个边界日期必须作为完整字面量出现（上界允许 `end+1` 的半开写法）；
  同时出现 `MAX(DATE(` 与 `DATE_SUB(非字面量)` 判定为自锚 → **阻止执行并说明原因**。
  宁可不给图，也不给"别的月份的数据 + 最近一个月的标签"。
- **空结果诊断按同窗口计数**：`empty_result_diagnosis_service.diagnose(time_range=..., time_field=...)`
  给每条 COUNT/GROUP BY 加时间底座。否则会出现「卡片说本月 13 条，诊断说去掉类目可查到 378 条」。
- **条件栏补齐确认值且可证伪**：agent 有时把品牌只写进 SQL、不写进 `plan.filters`，
  条件栏就只剩"时间"。`_verified_against_sql()` 仅在**字面量真出现在 SQL 里**时才补这一条。

### 5.3 验收（真实 agent + 真实 MySQL，HTTP 端到端）

```
问：优衣库品牌最近一个月上了多少件
选：优衣库（中国）

条件栏 = 品牌 =优衣库（中国） / 时间 =近1个月（2026-05-26 ~ 2026-06-25）
SQL    = ... WHERE b.Name = '优衣库（中国）'
                AND ci.CreateTime >= '2026-05-26'
                AND ci.CreateTime <  DATE_ADD('2026-06-25', INTERVAL 1 DAY)
rows_count = 5     ← 全部落在窗口内
自锚（MAX+DATE_SUB）= 无
```

同一句问「…多少件T恤」：本月优衣库（日本）**没有 T恤**（0 行）。
诊断按同窗口给出「去掉类目可查到 13 条」，不再出现全期的 378 条。

守卫：`tests/test_time_scope_enforcement.py`（11 条）+ 全量 **228 passed**，
`scripts/verify_canvas_all.sh` 全绿。
