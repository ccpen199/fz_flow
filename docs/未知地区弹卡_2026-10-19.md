# 字典里没有的地区 → 弹卡让用户选（2026-10-19）

> 一句话：`优衣库 韩国` 里的「韩国」在 `dict_brand_info` 里**没有对应标准值**，
> 这就等于**意图不明**——必须把真实存在的口径摆出来让用户选，不能把地区丢掉去取数。

## 1. 报障与用户要求

用户原话（2026-10-19）：

> 如果没有优衣库韩国 那就是相当于意图不明 需要谈卡片让用户选择！

背景：`dict_brand_info.Name` 里带限定的优衣库只有四条真实标准值
（官网 / 日本 / 淘宝 / 中国），没有「优衣库（韩国）」。

## 2. 旧行为（两条都是"猜"）

| 写法 | 路由结果 | 实际后果 |
| --- | --- | --- |
| `优衣库 韩国 …` | 「韩国」被当普通修饰词丢掉 → 裸 `优衣库` | ① 命中上一轮钉子（`优衣库（官网）`）→ **拿官网的数据回答韩国**；② 或查全地区混合数据 |
| `优衣库（韩国）…` | 拼成 `优衣库（韩国）` —— 一个**不存在的值** | 下游拿着假值去解析/查库，卡片还告诉用户"命中了 4 个候选" |

根因在 `intent_router._with_region_qualifier`：地区识别靠闭集
`REGION_QUALIFIERS = [官网, 日本, 淘宝, 中国]`，闭集之外**既不拼也不报**，
等于把"用户想换地区"这件事整个抹掉。

## 3. 现在的行为

1. **路由层**新增 `NON_STANDARD_PLACE_HINTS`（境外国家 + 渠道词）与
   `_region_qualifier()`，返回 `(brand, unknown_region)`：
   - 地区在闭集里 → `("优衣库（日本）", "")`（与旧行为一致）；
   - 地区不在字典里 → `("优衣库", "韩国")`：**品牌退回可解析的裸名，绝不拼假值**；
   - 认不出地区（`男装`、`PEACEBIRD`）→ 原样返回，不打扰用户。
   四种写法都认：`优衣库 韩国` / `优衣库（韩国）` / `优衣库韩国` / `韩国优衣库`；
   上下文只换地区（`那韩国呢`）同样识别。
2. **对话层** `_handle_turn` 拿到 `unknown_region` 且本轮是取数意图时，
   先走 `_ask_unknown_region()`（排在"没说方向"分支之前）：
   - 产出一张 `resolution_card`，候选是**字典里真实存在**的口径；
   - 回复先说明「标准品牌字典里没有「优衣库（韩国）」这个值」，再列候选；
   - **一个 SQL 都不跑**；候选为空时也不出空卡，只如实说明。
3. 点选之后标题落地：`品牌「优衣库（韩国）」需要确认` → `品牌「优衣库」已确认：优衣库（日本）`
   （留着"需要确认"等于说反话）。

## 4. 顺带修掉的一处自相矛盾

同一张图表卡里，条件栏显示 `品牌 =优衣库`，而 SQL 里是 `b.Name = '优衣库（日本）'`。
原因：`_run_goal` 内部会把条件对齐到本轮确认的标准值，但
`_execute_goals` 生成 `applied_filters` 时用的仍是 **agent 原话**。
现在 `_execute_goals` 先用同一套 `_merge_confirmations + _canonicalize_filters`
算一遍再渲染，卡片条件与 SQL 一致。

## 5. 验收

进程内真实链路（真实 agent 2124 + 真实 MySQL，不落盘）：

| 步骤 | 结果 |
| --- | --- |
| 轮 1 `优衣库 日本 近一个月上了多少件T恤` | 出图；条件栏 `品牌 =优衣库（日本）`，SQL `b.Name = '优衣库（日本）'` |
| 轮 2 `优衣库 韩国 …` | `resolution_card` / `needs_confirmation`，候选 官网·日本·淘宝·中国；文案明确说没有（韩国） |
| 轮 2' `优衣库（韩国）…` | 同上（不再拼出不存在的值） |
| 轮 3 点选 `优衣库（日本）` | 卡片 `ready`、标题改为已确认；按日本重新取数 |

## 6. 不做的事

- 不维护"全世界的地区词表"：只列**业务上真会出现的**境外国家与渠道；
  认不出来就按普通修饰词处理（`优衣库 男装` 不弹卡）。
- 不在路由层查库：路由保持离线确定，字典命中由对话层的 `resolve_brand` 做。
- 不猜"最近的地区"：`优衣库 韩国` 不会被自动换成「日本」或「官网」。
