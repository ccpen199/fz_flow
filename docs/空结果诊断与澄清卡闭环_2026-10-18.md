# 空结果诊断与澄清卡闭环（2026-10-18）

> 报障会话：`conv_dbc7be9bf4`（「优衣库这个月上了多少件 T恤」反复提示"查询执行成功但该口径下没有数据"）。
> 本文记录**根因定性 → 修复设计 → 实测证据**，改的是新画布链路（`agent.html`），老页面流程未动。

## 1. 定性：不是链路的锅，是口径/数据

用老链路 `/api/v1/sql-result-agent/sessions/{id}/generate-and-run` 复现同一问题，生成的 SQL 与新链路
**逐字一致**：

```sql
WHERE dbi.Name = '优衣库（官网）' AND ci.SubCategory = 'T恤'
```

两条链路都是 0 行。所以问题不在"哪条链路"，而在**标准值与该人群的真实取值对不上**：

- `clothing_info` 里「优衣库」是 4 个**互不相交**的实体（官网 417 / 日本 378 / 淘宝 348 / 中国 195，两两交集 0）；
- 官网这批数据里没有 `T恤` 这个二级类目，真实写法是 `T恤/Polo衫/背心`（121 条）；
- `T恤` 只存在于淘宝那套人群（66 条）。

## 2. 死循环是怎么形成的

```
0 行 → _ask_clarification(reason="empty_result")
     → _clarify_option_entries 写死只给「不限时间 / 仍限定在 X」
     → 用户点了，只改 time_window，SubCategory='T恤' 原样保留
     → 重跑必然还是 0 行 → 同一句提示再出现
```

而且点选项时后端只读 `time_window`，即使选项带了别的结构化字段也会被丢弃 —— 无论怎么点都出不去。

## 3. 修复

### 3.1 新增只读诊断：`empty_result_diagnosis_service`

原则是**能证伪才指认**：

1. 逐条剔除筛选条件重数，`rows_if_dropped > 0` 的条件才是候选堵点；
2. 多个候选都能"剔出数"时，用「该字段在剩余人群里的真实取值，是否包含用户说法的**同族写法**」定主犯
   （`T恤` ⊂ `T恤/Polo衫/背心`）。品牌这种用户明确选定的实体因此不会被误指成堵点；
3. 没有正向证据 → `checked=False`，调用方退回原有话术，**不猜**。

安全边界：

| 项 | 做法 |
|---|---|
| 读写 | 只 `COUNT` / `GROUP BY`，不写任何表 |
| 表名列名 | 只认 `scene.fields` 白名单 |
| JOIN | 只走 `scene.relations`（BFS 找路径），不自己编 |
| 计数 | 主表有 `Id` 用 `COUNT(DISTINCT 主表.Id)`，1:N 不放大 |
| 连接 | 统一走 `_connect()`，测试可打桩；任何异常 → `checked=False` |

> ⚠️ 期间修掉一个**潜在缺陷**：BFS 回溯给出的边顺序可能是「远端在前」（`main→A→B` 先拿到 `A-B`），
> 老实现按原序 JOIN 会 `KeyError`，被外层 `except` 吞成 `checked=False` —— 多跳关系的场景里诊断会
> **静默失效**。现在改为反复扫「至少一端已注册」的边，拼不出就显式抛错（仍是 fail-closed）。

### 3.2 澄清卡给真出口

诊断出堵点时：

```
[二级类目 改用「T恤/Polo衫/背心」（121 条）]   → set_filters
[去掉「二级类目 =T恤」这个限制（417 条）]      → drop_fields
```

卡片 payload 记住 `applied_filters` 与 `diagnosis`；用户点选项时 `_apply_filter_actions()` 把
`set_filters` / `drop_fields` 落到 filters 上（按规范名与 `raw_field_name` 双匹配）再送去取数。
只有**没有正向证据**时，才退回到「不限时间 / 仍限定在某窗口」两个选项。

### 3.3 `filter_missing` 改整值判定

`canvas_action_service._literal_present` 原来用 `text in sql` 子串匹配，`优衣库` 是 `uniqlo/优衣库`
的子串 → 把"口径不同"误判成"条件已生效"，静默出一张错口径的图。

现在解析 SQL 的单引号字面量集合，**整体相等**才算命中；两种例外仍然算命中：

- `LIKE '%优衣库%'`：字面量里含 `%`/`_`，是真实的模糊匹配；
- 日期前缀：筛选 `2024-07` 被写成 `>= '2024-07-01'` 是生效的。

### 3.4 别断言看不到的事实

规划器文案是在**取数之前**拼的，含"数据图表已在右侧生成"。当这一轮一个图都没成功（全空 / 全在追问）时，
改成"这次没有生成可展示的图表"。

## 4. 实测证据（真跑，非单测）

会话 `conv_63a1d5104f`，`scene_prd_structure`，问题「优衣库这个月上了多少件T恤」：

1. 品牌消歧卡选「优衣库（官网）」→ 澄清卡副标题 `这个筛选条件在本批数据里没有记录 · 选一个处理方式`，
   选项即 3.2 里的两条（121 条 / 417 条）；
2. 点「改用 T恤/Polo衫/背心」→ SQL 变为 `ci.SubCategory = 'T恤/Polo衫/背心'`，
   图表卡 `art_893012cb66` 出数（`rows_count=1`，narrative「2024-07-03 的 sku_count 最高，为 4」）。

死循环解开。

## 5. 顺带挖出来的另外四个隐患（同一轮全部修掉）

前面那条改完做**真跑复核**时又暴露出来的，都不是"看起来能用"，而是实测能看到错：

1. **用户写全名仍被要求消歧**：`intent_router._extract_brand` 只认品牌词本身，把
   `优衣库（官网）` 里的括号限定丢了 → 明明点名了官网，还要再弹一次 4 选 1。
   新增 `_with_region_qualifier()`：原文里确实写了括号限定才拼回去，只说 `优衣库`
   仍然要问（不猜）。
2. **诊断计数的人群不对**：品牌是写进 goal 文本的，不在 `filters` 里，所以诊断按**全表**计数，
   卡片会说"改用 T恤/Polo衫/背心（10814 条）"——而官网这批真实只有 121 条。
   `diagnose()` 新增 `fixed_filters`：已确认的品牌**参与每条 WHERE 的计数**，但**永不进候选池**
   （不许建议"去掉品牌"）。
3. **回复谎称出图**：见 3.4。
4. **结论文案漏出 `None`**：`str(row.get(field, "-"))` 在键存在但值为 `None` 时得到字符串
   `"None"`，实测出现「None 在sku_cnt上累计占比最高」。改为 `_label_text()` 归一成 `-`。

## 6. 追加：合并类目不能当"等价替换"推荐（用户质疑后修正）

用户看到卡片写「二级类目 改用「T恤/Polo衫/背心」」后直接质疑：二级类目不该是这种拼串。

**质疑成立，但结论不是"值改错了"，而是"我把合并标签当成了同义词"。**

### 数据事实（`dataservice_test_local.clothing_info`，实测）

| 事实 | 数值 |
|---|---|
| `SubCategory` 全表取值数 | 118 |
| `T恤`（细值） | 4353 条 |
| `Polo衫` / `背心`（细值） | 719 / 1274 条 |
| `T恤/Polo衫/背心`（合并标签） | 10814 条 |
| **优衣库（官网）**该字段 | **只有合并标签 121 条，没有 `T恤`** |
| `TertiaryCategory` / `QuaternaryCategory` | **全为空**（没有更细的类目字段可退） |
| `Category` / `SubCategory` / `LeafCategory` | 同一套值（`Category`=`SubCategory`，`Leaf` 只是小写） |

同一 `Source` 内部就混用两种粒度（`Source=1`：合并 8643 / 细值 2120；`Source=3`：合并 2171 / 细值 2208），
所以这不是"某个来源只给合并标签"，而是**行级标注不一致**。官网这批恰好全是合并标签。

### 修正

- `_alternatives()` 对"当前值正好是某合并标签的一个分段"（`T恤` ∈ `T恤/Polo衫/背心`）单独标
  `merged_parts`，与"拼写/别名差异"区分开；
- 卡片措辞改成 **`二级类目 只有合并标签「T恤/Polo衫/背心」（含Polo衫、背心，121 条）`**，
  answer 同步写成 `合并标签「…」（含Polo衫、背心）`，**不再出现"改用"**；
- 卡片正文（reason）也写成"这层类目只有合并标签「…」（含…），按它可查到 121 条"。

即：仍然给出可点的出口，但**明确告诉用户这是一锅端**，让用户自己决定要不要接受；
不再假装 `T恤` 和 `T恤/Polo衫/背心` 是同一件事。

### 6.1 四个「优衣库」实体逐个核对（2026-10-18 追问）

| 实体 | 总行数 | 类目 `=T恤` | 类目含 `T恤`（合并） | 商品名含 `T恤` | 合并标签占比 | 最新商品 |
|---|---|---|---|---|---|---|
| 优衣库（官网） | 417 | **0** | 121（`T恤/Polo衫/背心`） | 97 | 258/417 = 62% | 2024-07（≈2.3 年前） |
| 优衣库（日本） | 378 | **61** | 61 | 49 | 5/378 = 1% | 2026-06 |
| 优衣库（淘宝） | 348 | **66** | 66 | 78 | 4/348 = 1% | 2025-07 |
| 优衣库（中国） | 195 | **34** | 34 | 41 | 1/195 ≈ 1% | 2026-06 |

结论：**不是"优衣库没有 T恤 品类"，是"官网这个实体的这批数据没有细分"**。

- 官网的 417 行里 62% 是合并标签，且它的单值类目只有 短裤/裤装/连衣裙/运动裤… 压根没有 T恤；
  时间跨度 2020-06 → 2024-07，是**旧批次**（其余三个实体的最新商品都在 2025 年以后）。
- 日本/淘宝/中国 都是单值细分类目，`SubCategory='T恤'` 直接可查（61 / 66 / 34 条）。
  ⇒ 这是**数据批次/标注质量问题**，不是链路问题、不是配置问题。
- 顺手发现淘宝有 78 条商品名含 T恤但只有 66 条类目是 T恤（少量标注错位），属数据侧问题。

## 7. 追加：多轮里「换地区」不能沿用上一轮的品牌（用户追问"为何没弹卡"）

用户问「我想知道**优衣库 日本** 品牌最近一个月上了多少件T恤」，此前已经选过「优衣库（官网）」。
页面既没弹品牌卡、也没给日本数据，而是弹了一张 **T恤合并标签**的空结果卡。

### 根因（三段，逐段实测）

| 环节 | 旧行为 | 后果 |
|---|---|---|
| ① 品牌抽取 | `_with_region_qualifier` 只认括号写法 `优衣库（官网）` | `优衣库 日本` 里的「日本」被当普通修饰词丢掉，品牌仍是裸 `优衣库` |
| ② 钉住值匹配 | `_pinned_field_entry` 按**词面严格相等**命中 | 裸 `优衣库` 命中上一轮的 `优衣库 → 优衣库（官网）`，**直接用官网的数据回答日本** |
| ③ 条件合并 | `_merge_confirmations` 按 (table, field, term, value) 去重，官网与日本两条都留下 | `_canonicalize_filters` 按 (table,field) 建字典、后写覆盖先写 → **旧值把新值盖回去** |

另外 agent 这一轮确实回了 `needs_clarification=true`（问「日本是指站点还是品牌」），
后端把这句当附言，**照样去查了库**——"不确定就问"的约定在数据查询分支上没生效。

### 老页面对照（用户指出：老页面能识别）

老链路把**整句**交给 `field_value_resolver_service`，`_extract_lookup_terms()` 会把
`优衣库 日本` 当成一个 `qualified_phrase` 再解析。实测：

```
优衣库 日本 品牌…   → qualified_phrase '优衣库 日本'   → 优衣库（日本）  normalized_exact
优衣库日本品牌…      → qualified_phrase '优衣库日本'    → 优衣库（日本）  normalized_exact
日本优衣库品牌…      → mixed_phrase（老链路不认限定在前的写法）
```
新链路只把「品牌词」交给解析器，所以「日本」在更早一步就没了。

### 修正（4 处）

1. **地区限定做成闭集**：`intent_router.REGION_QUALIFIERS = ["官网","日本","淘宝","中国"]`
   —— 依据是 `dict_brand` 里带限定的优衣库标准值只有这四条（实测查表），
   所以「优衣库 男装」不会被误判成地区。识别三种写法：括号 / 空格或相连 / 限定在前。
2. **只换地区时接上下文品牌**：「那日本呢」「换成日本」「日本的」——去掉口头语后
   只剩地区词才接；「中国市场最近怎么样」这类还有别的实词的一律不接（fail-closed）。
3. **地区是替换不是叠加**：`working_memory.brand` 会被写成 `优衣库（中国）`，
   再说「官网呢」若直接拼会得到 `优衣库（中国）（官网）`（词典里不存在）→ 改为先剥旧限定。
4. **品牌槽位以最新说法为准**：
   - `_pinned_field_entry`：裸品牌（无括号）可沿用同词干的旧钉子；**本轮自己点名地区时绝不沿用**；
   - `_merge_confirmations`：一个 (table, field) 只留一个值，后写覆盖先写；
     `_run_goal` 里把**本轮解析结果放后面**，避免旧钉子覆盖新结果；
   - `_canonicalize_filters`：品牌字段例外，直接对齐到本轮解析值
     —— 否则上一轮 agent 带回的 `品牌 =优衣库（官网）` 会留在卡片条件栏里，
     SQL 却是日本，还会多报一句"品牌 =优衣库（官网）没能落到 SQL 里"；
   - 解析成功后 `_remember_brand_resolution` 写回会话（**只有 resolved 且非待确认才写**）。
5. **追问只在没产出时说**：`_data_query_trailing()` —— 这一轮出了图/卡就不再补 agent 的
   `clarify_question`；什么也没产出才原样转给用户。

## 8. 遗留
