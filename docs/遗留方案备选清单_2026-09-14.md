## A. 意图理解层

### ① LLM 语义路由（替换规则路由）

- **思路**：把 `IntentRouter` 从关键词打分换成 LLM 结构化输出（`{intent, entities, target_artifact}`），规则仅作降级兜底。
- **适用**：用户表达高度口语化、多意图混说（"顺便把色彩删了再出个图"）、需要槽位抽取（页数/时间窗/品牌别名）时。
- **代价**：引入时延（每轮多一次调用）、成本、不确定性；需保留"规则降级"通道（现有 `planner_mode: rules` 模式可直接沿用）。
- **本轮做法**：`intent_router.py` 规则优先，五类意图按优先级短路。
- **建议时机**：真实用户里出现"路由错分"投诉 ≥ 3 次后。
- **关键落点**：`intent_router.py` 的 `route()` 返回结构已与 LLM 输出对齐，替换成本低。

### ② 多意图合并解析（一个消息 → 多个 action）

- **思路**：一条消息拆成有序 action 列表（先删页 → 再换图 → 再导出），串行执行。
- **适用**：熟练用户"一句话干三件事"。
- **代价**：需要 action 依赖/事务语义（某步失败后面怎么办）。
- **本轮做法**：单意图，一次一条。
- **建议时机**：M2 之后，配合 ① 一起上。

## B. 体验与通信

### ③ SSE 流式进度（推荐优先做）

- **思路**：`POST /messages?stream=true` 返回 `text/event-stream`，分阶段推送 `routing → resolving → querying → charting → done`，前端进度条实时推进。
- **适用**：取数需数秒~十几秒，固定文案会让用户以为卡死。
- **代价**：需要处理事件流生命周期、断线重连、失败中途回滚语义。
- **本轮做法**：`setBusy()` + 固定文案"正在取数并出图（约 15 秒）…"。
- **建议时机**：**M2 首选**，投入产出比最高。
- **关键落点**：后端 `conversation_service.handle_message()` 已有清晰阶段划分，只需在各阶段打点。

### ④ WebSocket 双向通道

- **思路**：长连接，支持服务端主动推送（其他会话/他人改动）、协同编辑。
- **适用**：多人协作同一份 deck。
- **代价**：连接管理、鉴权、水平扩展复杂度。
- **建议时机**：引入多人协作时再考虑，单用户场景 SSE 足够。

### ⑤ 乐观 UI + 骨架屏

- **思路**：点击后立即插入"骨架卡片"，数据回来原地替换，减少等待感。
- **代价**：需要区分"占位/失败/重试"三态与真实卡片的 id 映射。
- **本轮做法**：`busy` 时禁用发送按钮 + typing 指示器。
- **建议时机**：与 ③ 一起做。

## C. 前端工程

### ⑥ Vite + Vue/React 框架化

- **思路**：把 `agent.js` 单文件拆成组件树（ChatStream / CanvasStack / CardRenderer / DeckPreview），引入响应式状态与虚拟 DOM。
- **适用**：卡片类型继续增加、画布交互变复杂（拖拽/嵌套）后，原生 JS 会越来越难维护。
- **代价**：引入构建链（打包/热更/CI）；与现有 no-build 交付方式不一致，交接成本上升。
- **本轮做法**：no-build 原生 JS，按 `kind` 分派渲染（`renderers[card.kind]`），新增卡片类型仍不改主循环。
- **建议时机**：卡片类型 > 8 种，或画布需要拖拽编排时。
- **关键落点**：现有 Artifact 协议（`kind` + `payload`）天然适配组件化，迁移时后端零改动。

### ⑦ ESM 组件化拆分（框架化的轻量中间态）

- **思路**：不引入构建工具，用原生 ES Module 把 `agent.js` 拆成 `transport.js / renderers/*.js / chat.js / canvas.js`。
- **代价**：需自行处理模块间状态共享。
- **建议时机**：想拆分又不想上构建链时，是 ⑥ 与现状之间的最优折中。

### ⑧ 画布拖拽编排 + 布局持久化

- **思路**：卡片可拖动排序、可置顶/收起/折叠，布局存入 `WorkingMemory`。
- **代价**：拖拽库/自研、移动端适配、布局冲突。
- **本轮做法**：固定插入顺序（`produced_artifact_ids`）。
- **建议时机**：用户明确要求"把这张图放前面"时。

## D. 报告与 PPT

### ⑨ 交接专业编辑器（TrainPPTAgent / presenton 路线）

- **思路**：画布预览只做"轻确认"，精修交回既有专业 PPT 编辑器（外链），导出后再回传绑定。
- **适用**：需要像素级版式、母版、复杂图元时，画布内编辑不划算。
- **代价**：跳转断链、两套状态同步（deck 版本 vs 编辑器版本）。
- **本轮做法**：画布内 16:9 HTML 近似预览 + 直接导出可编辑 pptx 兜底。
- **建议时机**：用户抱怨"导出后还要大改版式"时。
- **备注**：仓库里原 presenton 相关目录已清理（历史改动），若走此路线需重新评估接入对象。

### ⑩ 原生 pptx 图表（替换图片嵌入）

- **思路**：导出时写 python-pptx 原生 chart 对象，而非把 ECharts 图截图嵌入。
- **适用**：希望在 PowerPoint 里直接改数据/换图型的场景。
- **代价**：图型支持面收窄（原生 chart 不如 ECharts 丰富）；需放宽"前端与 PPT 一致性"要求。
- **本轮做法**：ECharts 出图 → python-pptx 嵌入图片，好处是两端 100% 同源（都走 `ChartSpecService`）。
- **建议时机**：客户明确要求"能在 PPT 里编辑图表数据"。

### ⑪ 页级局部重渲（改一页不重出全部）

- **思路**：编辑某页仅重算该页（补取数 + 重绑图 + 重写文案），其余页保持不变、保持稳定 id。
- **代价**：页面与图表的依赖追踪。
- **本轮做法**：改页走 `PATCH .../outline/pages/{pid}`，compile 时整体装配。
- **建议时机**：页数增多（> 8 页）后性能与体验需要。

### ⑫ LLM 语义级页-图绑定

- **思路**：让 LLM 判断"这页讲价格带，应该挂价格图"，而非按维度顺序挂载。
- **代价**：多一次调用、可能选错。
- **本轮做法**：`report_composer.build_outline()` 按已产出维度顺序启发式绑定，未绑定的标"待取数"。
- **建议时机**：出现"图挂错页"/"这页没图"反馈后。

### ⑬ 模板 / 主题中心

- **思路**：封面/目录/来源页/页脚规范、多套配色主题，按品牌或客户切换。
- **代价**：模板维护成本。
- **本轮做法**：单一样式（`agent.css` 深色主题）。
- **建议时机**：交付给多客户时。

## E. 数据与智能

### ⑭ 长时记忆 / RAG

- **思路**：把历史会话、分析结论沉淀为可检索知识库，新会话可"参考上次的结论"。
- **代价**：向量库、切分策略、召回质量、隐私边界。
- **本轮做法**：`WorkingMemory` 仅会话内有效。
- **建议时机**：用户开始问"上次那个结论是什么"时。
- **备注**：仓库已有 `semantic_cache_service`，可作为接入点。

### ⑮ 指标语义层 / 口径注册表

- **思路**：把"纤维占比""SKU数""价格带"等指标的口径（分子分母、过滤条件、时间窗）注册成受治理的指标卡，取数只引用指标名，不即兴写 SQL。
- **代价**：指标体系治理成本高，需要业务口径确认。
- **本轮做法**：依赖 `field_value_resolver_service` + `sql_result_agent_service` 的即兴生成。
- **建议时机**：出现"两次问同一件事结果对不上"时——这是口径漂移的信号。

## F. 架构与运维

### ⑯ MySQL 表化持久化

- **思路**：把 `CONVERSATIONS / MESSAGES / ARTIFACTS` 从状态字典落盘改为 MySQL 表，支持多进程与历史检索。
- **代价**：DDL、迁移、事务。
- **本轮做法**：随 `store.py` 现有状态一起写 JSON（`VIBE_PERSIST_STATE=1`）。
- **建议时机**：需要多实例部署或做会话检索时。
- **关键落点**：`store.py` 已把三张表集中管理，替换为 DAO 即可。

### ⑰ 长任务异步化 / 任务队列

- **思路**：取数、PPT 生成等重任务丢队列，前端订阅进度；避免请求超时。
- **代价**：引入 Redis/Celery 或自研任务表。
- **建议时机**：出现超时/并发瓶颈时，与 ③ 配合。

### ⑱ 场景自动路由（场景作为内部知识）

- **思路**：用户永远不选场景；系统按品牌/类目/意图自动匹配场景，匹配不到用默认场景兜底，配置中心降为二级入口。
- **本轮做法**：已部分实现——`create()` 不传 `scene_id` 时用默认场景 `scene_prd_competitor`，`working_memory.scene_locked_by` 区分"自动匹配/手动指定"。
- **建议时机**：场景数量增长后，需要多场景自动路由。

## G. 交付形态与边界（本轮明确不做）

| 方案 | 说明 | 何时考虑 |
|---|---|---|
| ⑲ 鉴权 / 多租户 / 权限 | 登录、数据行级权限 | 对外交付时 |
| ⑳ 定时报表推送 | 按周/月自动生成并推送 PPT | 成为日常机制后 |
| ㉑ 分享链接 / 只读快照 | 一次分析结果生成只读页分享 | 需要跨人传阅时 |
| ㉒ 协作编辑 | 多人同改一份 deck | 团队化使用后 |
| ㉓ 自动爬虫 / ETL / 写回 | 数据回流与写操作 | 明确不在近期范围 |

## 附：判断"该不该上"的三条经验

1. **规则够用时不上模型**：意图路由在样本 < 50 种表达前，规则更快更稳更省。出现明确误分再换 ①。
2. **等待感先解决再优化产物**：③（SSE）是体验性价比最高的一项，建议 M2 第一件做。
3. **口径问题优先级高于表现层**：若出现"同一问题两次结果不一致"，先做 ⑮（指标语义层），别急着做前端花活。
