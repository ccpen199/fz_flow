# 配置按需加载（轮次级配置）· 设计与落地

日期：2026-10-06
范围：**只改新画布**（`agent.html` / `agent.js` / `agent.css` + `apps/vibe_backend` 下 `/api/v1/conversations/*` 链路）。
老页面（`index.html` / `main.js`）一行未动——它走的是 `/api/v1/sql-result-agent/*`、`/api/v1/analysis/sessions/*`、
`/api/v1/scenes/*` 那套命名空间，与本次改动**零交集**。

---

## 1. 要解决的问题

### 现状：配置是「会话级、且粘性」

```
会话创建 → resolve_scene(关键词打分) → conversation.scene_id 定死 → 之后每一轮都用它
```

`handle_message` 里这段逻辑决定了这件事：

```python
if scene_id or conversation.scene_id is None:   # 一旦有过，就不再重算
    scene = self.resolve_scene(text=text, scene_id=scene_id)
if scene is None and conversation.scene_id:
    scene = scene_cache_service.get_scene(conversation.scene_id)
```

带来的三个具体问题：

1. **用户被锁死。** 会话开头问了价格带，后面想转而问纤维成分，用的还是价格带的配置。
2. **配置判定是关键词打分 + 默认兜底。** 实测：「价格带分布」被判到**竞品与价格分析**而不是价格带分析
   （"价格"命中竞品 +2、"价格带"命中价格带 +2，**2:2 平手**，遍历顺序里竞品靠前 → 先到者胜）；
   完全不相关的输入**静默落到默认场景**。这与「不确定就追问、不允许兜底」的既定原则直接冲突。
3. **不需要配置的轮次也在背配置。** "换成折线图""把第 2 页挪到前面"根本不需要字段与关系，
   却仍然挂着一整套配置。

### 目标

> **把配置从「会话属性」改成「轮次资源」：每轮由多轮 agent 按问题判定需要哪些配置，后端按需加载。
> 涉及配置就加载，不涉及就一个都不导入；同一会话的不同轮可以加载不同配置。**

## 2. 设计

### 2.1 配置目录（catalog）——让 agent 有依据地选

配置中心（MySQL `vibe_scene` / `vibe_scene_field` / `vibe_scene_relation`）里的每个配置，
都要能被 agent「看见」才谈得上选择。所以每轮把一份**目录**随 payload 发给 agent：

```json
"config_catalog": [
  {
    "scene_id": "scene_prd_price",
    "name": "商品价格分析",
    "description": "……",
    "sample_goals": ["看看各价格带的商品数与折扣力度", "…"],
    "field_count": 8,
    "fields": [{"semantic_name": "价格", "role": "metric"}, "…"]
  }
]
```

**落地时用的是配置中心里人工写好的 `sample_goals` 原句**（最多 4 条），而不是由后端再从里面抽一层 `topics`
关键词：原句本身就是最准的语义对照物，后端再抽一层等于又把"理解"挪回硬编码。
`description` / `name` 同样原样透传。代码里**不含任何业务词表**，新增一个配置**不需要改代码**，它会自动出现在目录里
（守卫：`test_service_has_no_hardcoded_scene_ids` 断言服务源码里不出现任何真实 `scene_id` 字面量）。

### 2.2 每轮判定：agent 多输出一个 `config_keys`

agent 的职责本来就是「理解这一轮想达成什么」。这一轮需要哪套配置，属于同一个理解动作，
所以**不额外加一次调用**——在现有判定里多回一个字段：

```json
{"intent": "...", "config_keys": ["scene_prd_price"], ...}
```

- `config_keys` 为空数组 = **本轮不需要任何配置**（闲聊、改画法、页码操作、回退…）。
- 可以多个（用户一句话同时要价格带和趋势）→ 后端合并加载。
- 白名单校验：不在真实配置目录里的 key 一律丢弃并如实记录，**不猜、不近义替换**。

### 2.3 按需加载与合并

```python
turn_config_service.load(keys) -> (SceneDTO | None, info)
```

- **0 个** → 返回 `None`，本轮**不加载任何配置**。
- **1 个** → 直接用该真实 `SceneDTO`（playbook / 价格带策略 / 问题矩阵全部正常）。
- **多个** → 合并成一个合成 `SceneDTO`：
  - `fields` / `relations` 取并集去重（关键：字段重叠度很高，见 §3）
  - `scene_id` 取**首个命中的真实 id**（不是自造 id）——因为
    `get_scene_playbook(scene_id)` 是按 id 查配置的，自造 id 会拿不到 playbook，
    从而丢掉价格带策略与问题矩阵，那是实打实的能力损失
  - `name` 形如「商品价格分析 + 趋势与爆款分析」，便于展示
  - 真实加载清单另记在 `info["config_ids"]`，进 `lineage`，保证**可溯源**

下游（`sql_result_agent_service` / `dimension_recommender` / `canvas_orchestrator`）
拿到的仍然是一个普通 `SceneDTO`，**一行都不用改**。

### 2.4 哪些轮次需要配置

| intent | 需要配置 | 原因 |
|---|---|---|
| `explore` | ✅ | 维度推荐依赖配置的字段资产 |
| `data_query` | ✅ | SQL 要字段与关系 |
| `report_build` | ✅ | 编译大纲时要绑图与取数 |
| `chat` | ❌ | 不产生任何产物 |
| `canvas_revision` | ❌ | 改的是画布上**已有**的东西 |
| `rollback` | ❌ | 版本回退 |

**需要配置但 `config_keys` 为空** → 纯文字**追问是哪个方向**，不出卡、不猜（沿用既有原则）。
**不需要配置的轮次** → 即使 agent 回了 key 也不加载（不引入无关的表与字段）。

### 2.5 给 agent 的字段词表

agent 写 `filters` 时需要知道「这个库里有哪些真实字段」。做法：

- 给出**全部配置字段的并集**（实测去重后只有 **36 个**，体量可控），
- 每项标注它属于哪些配置：`{"semantic_name": "价格", "role": "metric", "configs": ["scene_prd_price", "scene_prd_competitor", …]}`
- 后端随后用**本轮实际加载的配置**校验：字段不在其中 → 如实说明并追问，**不将就一个近似的列**。

这样既不存在「先有配置还是先有字段」的循环依赖，也保住了「条件必须落到真字段上」的约束。

### 2.6 可溯源

每一轮实际加载的配置写进两处：

- 助手消息的 `payload.config`：`{"config_ids": [...], "names": [...], "source": "turn"}`
- 图表卡的 `lineage.config_ids`

前端头部据此显示**本轮**加载了什么，而不是会话级的场景名。

## 3. 实测数据：为什么可以合并

对现有 5 个配置做字段重叠度统计：

| 配置 | 字段数 |
|---|---|
| `scene_0001` 品牌最新一条商品数据查询 | 11 |
| `scene_prd_price` 商品价格分析 | 8 |
| `scene_prd_competitor` 竞品与价格分析 | 29 |
| `scene_prd_structure` 商品结构分析 | 29 |
| `scene_prd_trend` 趋势与爆款分析 | 26 |

- **去重后并集：36 个字段**
- 被多个配置共用：**27 个**
- 只属于单一配置：**9 个**（原始标价/纤维编码/纤维占比/标准纤维名称/纤维标准编码 → 竞品；
  中文详情/外文详情/其他特征/适用性别 → 结构）

**结论：配置之间的差异主要不在字段，而在「关系（relations）、价格带策略、问题矩阵」。**
所以「按需加载配置」的真正价值落在：

1. SQL 上下文里**只出现本轮该用的表与 join**（不相关的表不进 JOIN，出错面更小）
2. 价格带策略 / 问题矩阵**只取自本轮命中的配置**
3. 维度推荐的范围收窄到本轮语境

| `handle_message` 内联做「按需加载」判定 | 抽成模块级 `plan_turn_config()` | 让三条规则**可被直接验证**（不依赖 LLM、不碰数据库） |

### 6.2 抓到并修掉的一个真 bug：闸门被架空

原写法：

```python
filters, rejected = canvas_action_service.normalize_filters(agent_plan["filters"], allowed_fields=...)
runs_query = bool(filters) or (intent == "data_query" and bool(picked_keys))
```

`normalize_filters` 的 `allowed_fields` 取自**本轮加载的配置**；没加载配置时它是空的，
于是**用户给的筛选条件必然被退回、`filters` 必然为空** → `runs_query` 恒为 False →
「要数据但没确定配置」这道闸门**永远不触发**。

症状（已由测试固定下来）：用户说「只看 400 元以上的」，收到的是
**「没能识别你给的筛选条件：字段「价格」不在当前场景的可查字段里」**——
这个归因是错的：字段在库里存在，只是这一轮根本没加载任何配置。

修正后用 agent 的**原始**判定做闸门：

```python
runs_query = turn_runs_query(intent=intent, filters=agent_plan.get("filters"), picked_keys=picked_keys)
```

文案改为「这一轮要用到数据，但我没能确定该加载哪一套配置，所以没有替你取数。点明方向就行……」，
并把被退回的条件说明合并进去。守测：`test_query_gate_refuses_to_run_without_a_config`。

### 6.6 环境阻塞（需要你处理）

**内网网关 `20.255.59.22:4000` 当前不可达**：

```
curl --noproxy '*' http://20.255.59.22:4000/v1/chat/completions  → 60s 超时，http=000
nc -z 20.255.59.22 4000  → TCP FAIL      nc -z 20.255.59.22 443 → TCP FAIL
curl https://www.baidu.com（直连外网）  → http=200
```

这不是本次改动引入的：`deploy/fz-workflow-demo.app.env` 里
`LLM_AGENT_HTTP_ENDPOINT` / `SQL_RESULT_AGENT_HTTP_ENDPOINT` 与 deer-flow `config.yaml`
的 `models[].base_url` 指向**同一个**网关，所以**新画布和老页面的取数此刻都会失败**。

表现：deer-flow 的模型调用在 ~75s 后重试，一轮判定跑不完；
新链路会走到既有降级路径 —— **如实说「多轮对话服务（DeepFlow agent）当前不可用，我没有替你猜意图」**，
而不是退回关键词猜（这正是"不允许兜底"的设计）。

**实测一条真实 HTTP 轮次**（`POST /api/v1/conversations/{id}/messages`，`text="看看 ZARA 的价格带分布"`）：

```
耗时 227.6s          ← 后端 120s 超时 ×2 次重试
ok        = False
status    = failed
error     = empty_reply
reply     = 多轮对话服务（DeepFlow agent）当前不可用，我没有替你猜意图。请确认 deer-flow 的
            LangGraph 服务已启动后再说一次。
canvas    = {}                          ← 零产物：没有猜、没有出卡
turn_config = {"config_ids": [], "names": [], "merged": false,
               "source": "turn", "note": "服务不可用，本轮未判定"}
```

即：**失败是"说出来"的，不是"猜出来"的**；头部胶囊也据此显示「未加载（服务不可用，本轮未判定）」，
与"本轮不涉及配置"区分开（守测 `test_agent_answers_but_gives_no_judgement_is_not_blamed_on_the_service`；
该守测已于 2026-10-07 加强，见 §6.7）。

**所以 §5 的「真实 LLM 多轮验证」这一步目前无法完成**，等网关恢复（需要连上对应网络/VPN）后按 §5 重跑一次即可；

## 6.7 修订：失败文案不再归错层（2026-10-07）

**问题**（用户在页面上截图反馈）：回复写的是

> 多轮对话服务（DeepFlow agent）当前不可用，我没有替你猜意图。
> **请确认 deer-flow 的 LangGraph 服务已启动后再说一次。**

但同期的分层实测是：**2124 的 LangGraph 服务健康**（`GET /ok` → `{"ok":true}` 200），
后端对它的 POST 也拿到了 200；真正不通的是它**调用大模型网关**（`20.255.59.22:4000`）那一跳
（`nc` 超时、`ping` 100% 丢包、agent 日志 `openai.APIConnectionError`）。

也就是说这句话把责任归到了**上一层**：用户照它去重启 LangGraph 服务，重启一百次也没用。
对照硬约束 ⑤（不兜底、如实说），"如实"不只是"承认失败"，还包括**别指错方向**。

**改法**：新增 `conversation_service.describe_agent_failure(error, *, agent_reachable)`，
判据**不是猜错误字符串，而是失败现场探测 `deepflow_agent_service.healthy()`**：

| 现场探测 | 原始 error | 回复正文（要点） | 头部胶囊 `note` |
|---|---|---|---|
| `/ok` 不通 | 任意 | agent 服务**连不上**（现场探测 /ok 也不通）→ 请确认 2124 服务已启动 | `agent 服务连不上，本轮未判定` |
| `/ok` 通 | `empty_reply` | agent 服务**是通的**，但这一轮没返回判定；通常意味着它内部调大模型失败 → 看 `deerflow_agent.log` | `agent 无判定结果，本轮未判定` |
| `/ok` 通 | 其它 | agent 服务是通的，但这一轮没能给出结果（附原错误码，截 60 字） | `agent 未返回结果，本轮未判定` |
| 未知 | 任意 | 不指定层，只说"没判定成功" | `服务不可用，本轮未判定` |

**为什么判据必须是探测、不能是错误串**：agent 服务"连不上"和"连上了但这一轮没出结果"，
在错误串上**都可能表现为超时**（后端等 `runs/wait` 超时 → `TimeoutError:timed out`），
光看字样分不开；而 `/ok` 探得通不通是当场的事实。守测
`test_timeout_is_not_blamed_on_the_service_being_down` 就是钉这一点的。

**措辞边界**：即使探测到"服务是通的"，也**不许断言"模型网关不可达"**——
那是后端看不到的事实，只能说"通常意味着它内部调大模型那一步失败了，请看它的日志"。
（这也是硬约束 ⑤ 的延伸：不确定就继续问/引导去看事实，不要替用户下判断。）

  `test_agent_unavailable_reports_it_instead_of_guessing` 改名并加强）：`empty_reply` + `/ok` 通
  ⇒ 正文含"是通的"、"deerflow_agent.log"，且 `连不上` / `已启动` **一个字都不许出现**
